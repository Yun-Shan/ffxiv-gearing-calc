# 已安装算法包的搜索性能分析

## 结论

当前搜索把每槽候选、食物、属性和伤害阶梯写成有界整数线性模型，再由 HiGHS 求解。已安装包中，**OR-Tools CP-SAT 是唯一有充分数学理由值得优先对照的替代求解器**：本问题本质上是有限域整数优化，CP-SAT 可用整数约束直接表达，并能在 WASM 内启用多搜索 worker。它可能更快，但目前没有相同输入下的对照测量，不能断言会更快，也不能因此省略精确因子复核。

GLPK 与 HiGHS 都属于 MILP 求解器；两者最坏情形都可能呈指数增长，但不同预处理、割、启发式和分支规则会让实际搜索树差很多。Ipopt 和 NLopt 面向连续优化，不能直接保留装备离散选择、取整阶梯和全局最优保证。

## 数学适配

设槽位 `i` 有有限候选集 `C_i`。搜索变量对每个装备槽作 one-hot 选择；有食物候选时，再对食物作 one-hot 选择。属性总和、食物取整/封顶、GCD 区间、坚韧和共享身份均转成整数变量及线性约束。伤害由整数阶梯因子乘积确定，求解器先最大化固定点对数和；随后通过 BigInt 对仍可能改进结果的因子签名进行精确比较。

| 已安装包 | 与模型的关系 | 是否可能更快 | 主要限制 |
| --- | --- | --- | --- |
| `highs@1.15.3`（当前使用） | MILP；分支割、LP 松弛、预处理、割和启发式 | 已有基准；当前 WASM 构建为单线程 | 状态仍来自浮点 MIP 求解，不能单独提供形式化证书 |
| `or-tools-wasm@0.7.1`（开发依赖） | CP-SAT；整数和布尔线性约束可直接表示本模型 | **最值得对照**。冲突学习、伪布尔传播及多 worker 可能改善难解实例 | 需要把 LP 模型改为 CP-SAT 原生模型并确认 int64 范围；浏览器多线程要求 COOP/COEP 跨源隔离，启用前需核对部署响应头；包目前是开发依赖 |
| `glpk.js@5.0.0` | 另一种 LP/MILP 求解器 | 理论上能求同一模型，但没有结构性理由预期优于当前 HiGHS | 仍需浮点 MILP；应作为实测基线，不宜按包名推断速度 |
| `ipopt-wasm@0.2.0` | 连续非线性内点优化 | 可为连续松弛提供局部试探解 | 装备变量连续化后会出现分数选择；局部连续解不证明离散最优 |
| `nlopt-js@0.1.1` | 连续优化 API（包示例使用 SLSQP） | 可尝试生成启发式起点 | 不原生求解该整数线性模型，也不提供所需的离散全局最优性结论 |

## 实际性能边界

`docs/搜索基准记录.md` 中，HiGHS 处理的完整联合实例耗时为 16.709 秒、42.735 秒和 132.538 秒，计时含基线、联合搜索和最优性复核；候选中每槽通常有数十个方案，戒指对候选可达数百。候选数量虽远小于全套笛卡尔积，但组合仍由跨槽、跨职业约束主导。

CP-SAT 的整数传播与并行搜索，可能降低联合模型的搜索树工作量；但模型构建、序列化和多线程开销也可能抵消收益。GLPK 与 HiGHS 虽然处理同类模型，共同的最坏情形复杂度不能预测具体实例速度；搜索树大小与实现开销都可能显著不同。Ipopt/NLopt 的连续结果本身既不是原问题的整数可行解，也不是有效的全局界；只有映射为完整装备方案并通过正式约束复核后，才可作为启发式起点或最大化问题的可行下界。

**建议：保留 HiGHS 为当前正式路径；若需要追求速度，先对 CP-SAT 做同输入、同约束、同停止条件的基准对照。** 对照必须比较精确 BigInt 目标和相同可行域，并把候选构造、模型编译、搜索及复核分别计时；只比较求解器内部时间可能得出误导结论。所有路径都应保留完整因子签名与最终目标复核。

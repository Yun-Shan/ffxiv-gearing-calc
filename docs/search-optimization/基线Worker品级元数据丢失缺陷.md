# 基线 Worker 品级元数据丢失缺陷

记录日期：2026-10-19。

## 现象与触发边界

VPR 在装备品级 770–795、无同步、DPS 目标、不限 GCD、默认推荐食物的联合独立基线中，返回了 `48.38157642779298`，低于此前合法配装的 `48.5175189601382`。两套配装的 GCD 都是 1.92 秒。

本机相邻提交对照确认，`4776415` 返回高分，`1901666` 返回低分。后者将本案默认食物候选从 32 个缩减为 17 个，但保留了高分配装使用的食物。将两份食物池在两版代码间互换，结果随食物池变化。这定位了本次回归的触发提交，不代表元数据缺陷或求解器内部问题最早引入于该提交。

历史高分装备及精确镶嵌变体仍在当前候选域中，按当前领域公式重算可复现原分数。该差异不能解释为旧配装不再合法或同步规则改变。

## 根因：Worker 传输契约遗漏品级

[基线执行器](../../src/domain/search/parallel-baseline-executor.ts)将装备候选编码为列式数组，发送给浏览器或 Node 基线 Worker。原协议保存了物品 ID、属性和戒指唯一性信息，却没有保存 `itemLevel`。[Worker 求解适配器](../../src/domain/search/parallel-baseline-solver.ts)解码时将每件装备的品级固定写为 `0`。

品级并非只用于展示。精确搜索会依据 `candidateItemLevelRanges` 判断哪些候选位于优化先验窗口外，再生成条件资源加强行；品级也参与资源预算候选上界策略的选择。将所有候选品级置零，会让线程内的优化策略偏离主线程。

这里须区分两个范围：

| 范围 | 本案数值 | 作用 |
| --- | --- | --- |
| 用户指定的合法装备品级范围 | 770–795 | 候选生成前的硬筛选 |
| 搜索优化的品级先验窗口 | 775–795 | 选择条件资源加强策略 |

先验窗口由最高品级减 20 得到，有同步时还会合并同步档位附近的窗口，见 [搜索准备](../../src/domain/optimizer/search-preparation.ts)。它不限制合法候选必须处于该窗口内。

本案 723 个候选变体中，475 个品级为 770，110 个为 780，121 个为 790，17 个为 795。真实品级下有 475 个候选处于先验窗口外，置零后变成全部 723 个。

## 对正确性的影响

### 硬品级筛选没有被绕过

[装备筛选](../../src/domain/gear-options.ts)在进入 Worker 前，已依据真实品级索引及职业规则完成合法性检查；有效属性、同步与镶嵌也已计算。Worker 只在传入候选中选择，并将候选索引交回主线程还原为原始装备对象。因此，品级置零不会凭空引入范围外装备，也不会使已生效的同步属性恢复。

### 条件加强模型发生变化，但本案未发现错误切除合法解

只恢复装备品级，保留其他 Worker 重建行为，对照得到：

- 两模型均为 2175 个变量、374 条约束；变量边界、目标函数和完整初始提示完全一致。
- 仅 22 条条件资源加强行变化：11 条普通行和 11 条加权行。其余 352 条约束一致。
- 恢复品级并不会让这些行消失，因为真实候选中仍有先验窗口外装备。

以耳坠槽为例，普通条件行的激活候选由 49 个变为 41 个；加权条件行的激活候选由 57 个变为 41 个，候选变量的附加系数从 54 变为 228，右侧预算仍为 110351。

条件行的预算来自真实属性，不按品级猜测属性上限。记各因子类别属性下界的非负加权和为 `R`，某槽的资源最大值为 `M`，全局资源预算为 `B`。对资源不超过阈值 `t` 的候选子集 `A`，加强行为：

```text
R + (M - t) × Σ(x_i，i 属于 A) ≤ B
```

选中 `A` 内候选时，该槽资源至多为 `t`，附加项补到 `M`；未选中时附加项为零。只要 `A` 中候选确实满足资源阈值，该行仍成立。品级分类错误会改变 `A` 和阈值选择，但不直接推导出该行无效。

调查对置零与真实品级模型的共 44 条条件行，独立使用 BigInt 计算各槽候选及食物贡献的保守资源上界，全部满足对应预算。该检查覆盖本案全部合法组合，而非仅检查历史配装；结论不扩大到其他职业的可变参数武器等情形。

### 求解器错误最优判定仍须单独看待

将原模型直接交给 HiGHS 重放，历史高分完整整数赋值在原生矩阵中仍满足所有约束。其代理目标为 `-4265003.020706177`；求解器却对较差的 `-4307817.038269026` 返回 `Optimal` 和零差距，最大化目标下两者矛盾。

移除条件加强行、关闭求解前提示或关闭自动重启搜索，均曾恢复高分对应目标。恢复真实品级后，保留全部原策略、热启动和自动重启，也恢复高分。因此本修复纠正了可确认的数据契约缺陷，但不宣称已定位或修复 HiGHS 内核的具体错误。依赖首次代理最优界的后续签名带检查也不能独立排除此类错误判定。

## 修复

在 `SerializedEquipmentColumns` 增加 `itemLevels: Float64Array`，编码时逐候选保存真实品级，Worker 解码时逐候选恢复，并验证品级列长度与候选数量一致。

使用 Float64 列与现有数值列保持一致，不引入窄整数截断。该结构仅用于同版本运行时 Worker 消息，不改变游戏数据二进制格式或持久化数据。修复不调整食物筛选、候选排序、约束公式或 HiGHS 求解选项。

## 回归与复现

[执行器测试](../../src/domain/search/parallel-baseline-executor.test.ts)检查混合品级的编码、原候选对象还原，以及本地和 Worker 的条件加强策略一致性。[解码测试](../../src/domain/search/parallel-baseline-solver.test.ts)检查先验窗口两侧的品级恢复、错位数值列、无效偏移及求解配置传递。

在仓库根目录运行：

```powershell
npx vitest run src/domain/search/parallel-baseline-executor.test.ts src/domain/search/parallel-baseline-solver.test.ts --exclude "docs/**"
node docs/search-optimization/tools/run-acceptance.mjs --case brd-dnc-mch-vpr-unsynced-independent-dps
```

修复后的真实基线 Worker 已返回 `48.5175189601382`；723 个候选的品级传输往返一致。高分总属性为灵巧 6490、暴击 928、信念 2824、直击 2475、技速 2393，与历史高分一致。

本次验证记录：

- 两个定向测试文件共 21 项测试通过。
- 解码适配器覆盖率：语句 94.93%、分支 90%、函数 100%、行 100%。执行器整体覆盖率为语句 87.71%、分支 70.34%、函数 100%、行 91.42%，其调度及异常处理分支未全部覆盖；不据此宣称两文件整体达到 90% 门槛。
- 应用与工具 TypeScript 检查、生产构建通过。本机原构建缓存存在写权限限制，因此分别执行两个项目的类型检查，并将构建产物输出到独立临时目录。
- 全场景验收按用户要求停止。已完成前 10 个场景，均通过结果合法性及完整证明检查；其中两个超过每职业 30 秒的性能目标。第 11 个场景执行中停止，其余未执行，不作为完整全场景验收通过。

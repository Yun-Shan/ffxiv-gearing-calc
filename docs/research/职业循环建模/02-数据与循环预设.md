# 数据、动作规则与内置循环预设

研究提案，2026-10-23。返回[总览](README.md)。本文定义数据职责与失败语义；数学定义见[01](01-模型数学与多GCD系数.md)，来源证据见[07](07-来源与探索证据.md)。字段名仅用于解释契约，尚未变成生产 API 或二进制 Schema。

## 1. 先区分事实、策略与系数

同一个最终分数需要三种不同性质的输入，不能混为“游戏数据”：

| 层次 | 内容 | 来源与所有者 | 更新触发 |
| --- | --- | --- | --- |
| 游戏事实 | 技能等级、威力、命中规则、消耗、触发条件、buff 与取整 | 同版本资料与已核验规则；遵守数据来源优先级 | 游戏版本/语义改变 |
| 行为策略 | 默认动作策略、目标数、持续时间、增益场景、初始资源、消耗时机 | 项目明确选择并说明的模型假设 | 产品场景改变或验证不再成立 |
| 编译系数 | 某 GCD 下普通/必暴威力贡献、资源事件次数、时间分母等 | 规则与策略的确定性推导结果 | 任一依赖改变 |

游戏资料不可能直接告诉程序“所有玩家在 1.94 GCD 下应该使用哪些动作、会获得多少队友斗气”。这些必须由明确策略推导。另一方面，不能把某套装备、某段日志的最终伤害比例冒充游戏固定常数。

本项目禁止生产虚构/近似游戏数据，且当前搜索目标已有明确规范。引入分析模型必须将**真实技能规则与模型场景假设分开**，并在生产启用前确认评分语义、支持范围及规范变更。本文授权范围是研究与文档，不表示已批准把合成实验权重用作默认循环。

## 2. 当前数据边界与已知缺口

现有 bin 供浏览器、Worker 与 Node 共用，但没有可以直接充当完整战斗引擎的动作语义。研究时读取的 bin、Lumina MCP 和国际服指南版本也未对齐，详见[证据版本表](07-来源与探索证据.md)。

已发现的具体缺口是 `ActionTransient` 的动态威力文本不总能完整返回。不能通过空字符串补零、把某个等级的威力复制到其他等级，或从名字推断必暴条件来“补全”。动作命中条件、触发例外及 buff 转换也不能只靠有无某个布尔字段决定。

生产接入顺序应为：

1. 明确目标游戏版本和受支持计算等级，按项目数据规则查询 Schema 与资料。
2. 区分“字段不存在”“动态文本没展开”“关联表没查”“工具能力不足”，先排除调用错误。
3. 只有确认 MCP 缺少必需资料后，才调查项目允许的参考来源。新来源不在现有白名单中时先更新规则，不能借研究引用自动赋予生产来源资格。
4. 给每项技能规则标记核验状态；必需项缺失或版本不一致时阻止对应 profile 编译。
5. 如需新的运行时业务字段，由统一生成器和编解码契约生成；不手改 bin，不另写绕过统一更新入口的动作 JSON。

本次专题拆分复用同一会话已取得的研究依据，没有更新游戏数据，因此没有重复查询 MCP 或重生成 bin。未来全量生成必须按当前规则先完成 `refresh_schema`，再继续健康检查与查询。

## 3. 预设应当表达什么

预设是确定的行为与计分契约，不是一张永远不变的属性权重表。

| 字段组 | 建议表达 | 必须避免 |
| --- | --- | --- |
| 身份 | 规则定义 ID、内容摘要、职业、计算等级、场景 ID | 仅凭职业缩写共用所有等级 |
| 支持域 | 已验证的 GCD/速度依赖范围、目标数、时间模型 | 把有限支持写成所有场景 |
| 策略 | 动作使用策略与规则，或已有依据的动作次数模型 | 要求用户手填完整技能序列 |
| 资源 | 初始值、哪些事件触发、概率、成本、上限、消耗策略 | 只缓存某个参考暴击率下的触发次数 |
| 增益 | 自身/外部来源、持续区间、重叠与快照假设 | 把所有技能一律乘平均覆盖率 |
| 时间 | 固定时窗、长期周期或每事件评分；单位明确 | 周期总伤害与每秒数值直接比较 |
| 输出 | 有理系数、依赖坐标、公式能力和适用证明后端 | 任意回调函数直接取得精确求解信任 |

同一 GCD 若允许多种策略，必须选择以下一种明确语义：固定默认策略；或将有限策略集合也作为优化域。后者新增 `policy` 选择，最终承诺仅针对列出的策略集合，不能宣称同时优化了所有可能循环。

## 4. 多 GCD 系数的生成流程

建议流程是 `规则＋场景＋策略 → 适用域解析 → 系数编译 → 依赖检查 → 数学能力检查 → 冻结目标`。

### 4.1 先求实际允许域

用户选择的 GCD、速度上下界、等级、食物、装备限制与其他硬约束共同决定实际可达档位。预设支持域与实际可达域是两件事。

- `无可行配装`：该档在当前候选和全部硬约束下不可达。
- `模型不支持`：可能有合法配装，但没有经核验的规则或策略。
- `尚未证明`：搜索未完成，不能把它当成无解。

三种状态必须区分。如果实际可达域包含模型不支持档位，不能悄悄删去这些档位后返回“用户允许范围内最优”。可报告不支持并要求明确选择已支持范围/通用目标；产品若要预先约束选择域，需要单独确认界面契约。

### 4.2 系数来自使用次数，不来自最终伤害比例

普通/必暴贡献通常由 `动作次数 × 基础威力 × 适用状态` 推导。斗气触发次数还要按事件资格单独计数，不能由威力占比倒推。固定冷却动作的每秒频率也不能简单乘 `1/GCD`。

一个可复用的编译结果可以是基函数系数，例如 `N(c,k)`、`K(k)`、`cN(c,k)` 的有理线性组合。保留依赖暴击率的项，换装时再求值；不要先把 `c=某个参考值` 代入并永久固化动作数量。

各档编译必须遵循相同场景和单位。若采用周期总量，需要保存真实周期时长；如果已经生成每秒系数，就不再除 GCD。正比例常数能否约去，取决于它是否对**整个比较域**恒定，而非只对一个分支恒定。

### 4.3 不以插值代替规则

跨 GCD 时可能跳变的是动作数、窗口内能容纳的技能、资源消耗时机及末尾动作。这些不能默认线性插值。可选方式为逐个支持档位编译，或者证明某个速度区间内行为相同后共用。

“面板 GCD 相同”也不足以证明整个行为相同。模型使用其他技能复唱、施法、DoT/AA 速度倍率或增益后的时间时，应将真实依赖加入签名，而不是一律压缩到两位小数的基础 GCD。

## 5. 资源与时间模型的等级

| 模型 | 优点 | 适用边界 |
| --- | --- | --- |
| 长期平均、无溢出 | 易形成有理系数，便于精确比较与搜索 | 不含尾段余数、资源上限损失、时间分布相关性；应称模型评分 |
| 固定事件序列的有限状态期望 | 可明确处理初始/结束资源、上限和消耗策略 | 需要证明状态转移与时间语义完整，可能使 CRT、速度和事件序列耦合 |
| 自适应时间策略 | 更接近预设模拟器，能随资源与速度改变后续动作 | 状态规模、数值大小、安全界和证明成本更高；不自动适合现有 MIP |
| 随机采样模拟 | 适合评估分布或独立比较样本 | 样本均值不能直接作无误差的最优目标或安全剪枝界 |

长期平均资源除以成本可以是明确的分析假设，但不是有限时窗的精确技能次数。已有精确二项分布反例见[07](07-来源与探索证据.md)。正式增加状态模型时应保留每个受支持等级的触发、资源上限、使用资格和尾段约定，不能仅调一个全职业倍率。

## 6. 最小数据契约示意

以下是设计草图，不是要直接加入生产的现成 Schema：

```ts
type Rational = { numerator: string; denominator: string };
type CompiledProfile = {
  definitionId: string;
  definitionDigest: string;
  jobId: string;
  calculationLevel: number;
  scenarioId: string;
  scoreKind: "model-score" | "expected-dps";
  timeBasis: "periodic" | "finite-window";
  dependencies: readonly string[];
  rows: readonly {
    gcdCentiseconds: number;
    policyId: string;
    coefficients: readonly Rational[];
    durationSeconds?: Rational;
  }[];
};
```

有理数以字符串传输只是避免 JSON/Number 失真；实际格式应复用项目类型约定。编译器必须校验正分母、有限支持域、非负项或其他目标假设、来源完整性、依赖坐标，以及对应求解后端的表示范围。字符串合法不代表公式正确，也不代表能进入 `roundedLog(Number)`。

身份不应含任意临时对象地址。可重现的定义、场景、参数和支持域产生稳定内容摘要；摘要只用于确定输入身份，不能代替规则和支持域校验。

## 7. 缓存与 Worker

可以复用规则解析、动作分类和确定的编译结果；动态求值只有在输入完全一致时才可缓存。

- 编译缓存至少区分规则定义、职业/计算等级、策略、场景及适用速度域。
- 动态结果区分目标所有依赖；武僧资源反馈不能只按 GCD 缓存。
- 候选与可达性缓存还依赖装备/食物/同步/强制约束及资源政策，不能仅按模型 ID 跨搜索复用。
- 一次搜索冻结目标与场景；Worker 收到可序列化定义或可核验的编译描述，再重建同一求值器。不能让主线程用新 profile、基线 Worker 用旧公式。
- 取消后不得留下可被新任务当作已完成结果的半成品；并行任务使用有界缓存和独立可变求解状态。

## 8. 固定配装、历史与产品边界

用户不需要排循环，但应能知道分数用了哪个模型与假设。新增评分名称、模型选择和支持域提示属于产品契约变更，实际界面实现仍须按项目规则确认。本文不新增页面或控件。

固定配装计算不应启动装备优化。如果同一装备在模型支持域内，可直接按其实际 GCD 求职业分数；缺少支持时明确缺项，不能偷偷搜索成另一个 GCD 的装备。

历史沿用“保留原值、载入不重算”的规则。旧历史没有新字段时明确解释为 legacy 目标；新历史冻结实际使用的模型定义、场景与系数身份，使其可以解释，重新编辑再搜索才重新解析支持域。现有 `dataVersion` 仍只是展示元数据，不把游戏数据版本变成历史强制迁移开关。

分享链接主要描述装备与现有配置，不能据此假定带有完整模型定义。未来要传播模型语义，需要有明确协议及兼容行为；这不影响当前完整槽位、固定镶嵌与自定义参数的验证。

## 9. 哪些条件满足后才能启用

必须同时具备：同版本必需动作规则、明确行为假设、系数来源和单位校验、适用域覆盖、固定配装对照、数学能力与后端匹配、Worker/历史语义一致。模型数据缺失时停止对应模式；性能预算不足时是否可回退，取决于是否已经有**同一目标**的完整基础路径，详见[05](05-通用建模与耗时优化.md)。

最先需要决定的是最高等级的默认单体场景和计分语义。没有动作依据之前，研究脚本的 75/25 等数字只能留在隔离实验中。

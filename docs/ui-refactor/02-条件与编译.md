# 条件与编译

[返回入口](README.md)。来源：[最终设计补充](https://github.com/Yun-Shan/ffxiv-gearing-calc/issues/2#issuecomment-6210161797)为主要契约，正文仅保留未被覆盖部分。

> 等级规则与现行领域规则有实质冲突；UI 阶段先通过 mock 完成组件测试，全部 UI 完成后、最终 Playwright 前再由用户确认具体 domain 方案，见[冲突与修改边界](00-冲突与修改边界.md)。以下是目标设计，不是实施授权。

### Domain：等级规则

不再使用候选装备推导公式等级。

需要明确区分三个概念：

- `jobMaxLevel`：职业当前最高等级 / 可穿戴等级上限。
- `syncItemLevel`：同步品级（现 `syncLevel` 实际语义，建议重命名）。
- `calculationLevel`：公式、基础属性、GCD 等使用的等级。

规则：

```text
wearableLevel = jobMaxLevel

calculationLevel = syncItemLevel 存在
  ? min(syncItemLevel 映射出的职业等级, jobMaxLevel)
  : jobMaxLevel
```

候选装备筛选仍使用 `wearableLevel`，不要因为低等级同步而排除高装备等级、可穿戴的装备；装备属性本身继续按 `syncItemLevel` 做同步 / cap。

因此应删除现有候选派生公式等级逻辑，包括 `HighestCandidateGearLevel`、`preferCandidateGearLevel` 以及 candidate-pool highest level 对 calculation level 的影响。

### Joint objective

Per-job objective 继续由各职业自己的 GCD 条件语义推导：

- 一个确定 / 可行 GCD → `damage`
- 多个可能 GCD → `dps`

UI Draft 不保存 objective。

当前 domain 的 Joint 仍只支持一个 global objective，此限制本次先保留。Compiler 做兼容归一化：

```text
所有 job objective 都是 damage
→ Joint global objective = damage

否则
→ Joint global objective = dps
```

并把当前编译出的各 `OptimizationConfig.objective` 归一为该 global objective，以满足现有 domain 限制。

未来 domain 支持不同职业使用不同 objective 时，只移除这层兼容归一化，不改 Job Draft / GCD 语义模型。

## 通用职业条件

JobConditionDraft 包含 range、gcd、food、tank。range 包含装备品级 min/max，以及 disabled/enabled + itemLevel 的同步判别联合。UI 不提供角色/职业等级输入，不用范围最高候选决定计算等级；由编译边界落实上述职业上限与同步规则。视觉合并为“搜索范围”：装备品级、同步品级、自动等级说明。

## GCD

```ts
type GcdDraft =
  | { mode: "any" }
  | { mode: "tiers"; tiers: number[] }
  | { mode: "speed"; min?: number; max?: number };
```

规则：

- `speed` 允许只填最小值、只填最大值或双边界。
- 两边都空无效；`min > max` 无效。
- mode 切换直接丢弃旧 mode 数据，不保留隐藏配置。
- 自由文本 `gcdChoicesText` 删除，tiers 直接从可行档位选择。
- `objective` 不进入 Draft，由 compile / validation 基于 GCD 语义推导。

### GCD editor runtime

```ts
type GcdAnalysisState =
  | { status: "idle" }
  | { status: "loading"; key: string }
  | { status: "ready"; key: string; feasibleTiers: number[] }
  | { status: "error"; key: string; message: string };
```

`useGcdAnalysisController()` 负责 debounce / AbortController / `findFeasibleGcds` / runtime 更新；组件只编辑 Draft 和读取 runtime。

Analysis key 应由显式 `GcdAnalysisInput` 生成，只包含真正影响可行 GCD 的字段，不要 stringify 整个 Draft 后再删字段。

## Food

`FoodDraft` 继续属于 `JobConditionDraft`。

Joint shared 维护：

```ts
interface JointSharedDraft {
  foodStrategy: "shared" | "independent";
  sharedFood: FoodDraft;
  // ...
}
```

- `shared`：共享 food 生效，私有 Food UI 禁用，但各职业私有值保留。
- `independent`：各职业 food 生效，共享 food 保留但暂不使用。
- 切换 strategy 不清空任一侧配置。

共享 Food 使用独立 `FoodStrategySection`，职业内 `FoodSection` 继续复用。

## Joint Equipment：排除与强制的最终语义

#### Shared settings

```ts
interface JointSharedEquipmentDraft {
  excludedSources: string[];
  excludedGearIds: number[];
  forcedGear: Partial<Record<GearSlot, number>>;
}
```

- `excludedSources`：全职业、全槽位生效。
- `excludedGearIds`：全职业禁用该物品，无论该装备类型当前是 shared 还是 private。
- `forcedGear`：只能设置 shared slots。

Shared 的“排除指定装备”picker 按装备类型 / 部位过滤可选列表。

#### Job settings

```ts
interface JointJobEquipmentDraft {
  excludedGearIds: number[];
  forcedGear: Partial<Record<GearSlot, number>>;
}
```

- Job `excludedGearIds`：一旦设置，该职业完全不能使用该物品，**不按槽位生效**。
- 但只有某装备类型当前至少存在一个 private position 时，Job Editor 才允许新增该类型的排除。
- 戒指按装备类型处理：若 `ring` shared、`ring2` private，Job 仍可排除某枚戒指；一旦排除，该职业在 shared ring 与 private ring2 都不能使用它。
- 若某装备类型失去最后一个 private position，则清理该 Job 对该装备类型的 exclusions，避免纯 shared 类型留下不可编辑的隐藏 Job restriction。
- Job `forcedGear` 只能设置 private slots。

因此 **Exclude 是 item-level restriction，设置资格按 equipment type；Force 是 slot-level restriction，设置资格与生效范围都按 slot ownership。**

`OptimizationConfig.excludedGearIds` 当前的 item-level execution 语义可以继续使用，不需要改成 slot-scoped exclusion。

#### shared/private ownership transaction

- private → shared：清除所有 job 在该 slot 的 private forced gear。
- shared → private：清除 shared forced gear。
- forced gear 不在 shared/private scope 间自动迁移。
- exclusion 只按上述“装备类型是否仍有 private position”的规则清理，不按单个 slot 粗暴清除。

Joint shared solver candidate 仍由 domain 对各职业候选池按完整 `equipmentIdentity` 求交集；UI shared picker 只需保证物品本身对所有职业合法，不需要在 UI 预求完整 meld identity。

## 装备事务补充

Single 保留 excludedSources、excludedGearIds 与全槽位 forcedGear。Joint Shared 与 Job 使用上面的独立类型，不做万能 EquipmentDraft。

- 强制一件已排除装备时，移除对应 excludedGearIds；排除当前强制装备时，清掉对应 forced slot。
- 排除来源时，清掉来自该来源的强制装备；Joint shared 来源事务同时检查 shared 与所有 job private forcedGear。
- 单独 excluded 的物品即使来源也被排除仍保留，不自动清理。
- Joint Job 有效物品排除为 shared 与 job 排除的共同作用；来源排除从 shared 派生，不复制进各 job Draft。强制装备的合法候选同时受实际有效条件与槽位 ownership 约束。

上述更新为语义事务，不能让组件通过多个独立 setter 暂时留下矛盾配置。戒指按装备类型清理 exclusion、按具体位置处理 force，不能混淆。

## Validation：一个同步的派生快照

Validation 不进入 Workbench store，而是从当前 Draft + EditorRuntime **一次性派生完整不可变快照**。Main、Aside、各 Section 都从同一个对象读取，子组件不要再次调用 `validateXxx()` 独立计算。

建议树形结构：

```ts
type ValidationStatus = "valid" | "invalid" | "pending";

interface SectionValidation {
  status: ValidationStatus;
  issues: readonly ValidationIssue[];
}

interface WorkbenchValidation {
  status: ValidationStatus;
  valid: boolean;
  issues: readonly ValidationIssue[];
  shared?: SharedValidation;
  jobs: Readonly<Record<JobId, JobValidation>>;
}
```

同一个 issue 应能同时从 section branch / job branch / root issues 中看到；这些是同一批 issue 的聚合，不是重新生成三次。

聚合优先级：

```text
存在 invalid → invalid
否则存在 pending → pending
否则 → valid
```

GCD 异步分析的 loading / idle 属于 `pending`，不是普通 error。

Domain 仍保留 execution config 的最终硬校验；Workbench validation 负责编辑器是否可提交。`no-result` 属于合法搜索结果，不属于 validation error。

Search controller 在真正开始搜索时必须重新读取最新 Draft/runtime 和最新 validation，不依赖按钮 render 时的旧值。

Conditions Aside 从这一份 validation 直接派生提示与“开始搜索” disabled 状态，Page 不参与。不要保存 statusText/statusReady/canStartSearch。

## 编译与恢复验证

语义 round-trip 使用 normalizeCompiledDraft，而非 deepEqual 原始编辑对象。覆盖 mode 切换丢弃值、Food 编辑会话保留值与编译后丢弃未生效值、Joint 目标归一化、共享/私有限制、同步等级。执行配置最终硬校验仍由 domain 负责，不能以 UI validation 代替。

## 尚需明确的编辑冲突

Issue 将 Joint shared exclusions 扩大为全职业有效后，没有补全所有跨 scope 事务：例如某 Job 强制物品已被 shared 排除、shared 强制戒指被另一 Job 排除，或者来源排除与新增强制互相矛盾。现有“force 移除 exclusion / exclude 清除 force”规则未指明跨 scope 时允许改动哪些 Job。

实施前需用户确认跨 scope 的处理顺序与修改范围；不得悄悄删除其它职业限制，也不得让矛盾配置绕过 validation。记录该未决项不阻止独立组件与 mock 测试的推进。

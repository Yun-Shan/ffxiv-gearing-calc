# 架构与状态

[返回入口](README.md)。来源：[Issue 正文](https://github.com/Yun-Shan/ffxiv-gearing-calc/issues/2)、[最终补充](https://github.com/Yun-Shan/ffxiv-gearing-calc/issues/2#issuecomment-6210161797)、[源码所有权](https://github.com/Yun-Shan/ffxiv-gearing-calc/issues/2#issuecomment-6210358727)。

## 职责

Page 只建立 Provider/scope 与布局；Main/Aside 自行按 phase 切换。store 保存同步业务状态，controller 承担异步副作用。feature section 在 scope 边界读取，primitive UI 为 props-only。静态 label/template/schema 不进状态，派生值用 selector/纯函数，不保存 panel 文案、按钮回调或 presentation snapshot。

### Workbench phase 中不再有 Conditions feedback

顶层 phase 收敛为：

```ts
type SingleWorkbenchState =
  | { phase: "selection" }
  | { phase: "conditions"; draft: SingleWorkbenchDraft; runtime: SingleEditorRuntime }
  | { phase: "progress"; snapshot: OptimizationConfig; progress: SingleSearchProgressState; startedAt: number }
  | { phase: "result"; snapshot: OptimizationConfig; result: OptimizationResult; durationMs: number };
```

Joint 同构，Snapshot 与 Result 分别使用 JointOptimizationConfig、JointOptimizationResult。phase 示例未展开的来源版本与 historyId 上下文见[搜索与历史](03-搜索与历史.md)。

`feedback?` 从 Conditions phase 删除；所有一次性反馈统一走 Toast / Modal。

## Draft 与执行配置

Draft 只在 Conditions 存在。开始搜索编译并冻结 Snapshot，销毁 Draft；Progress/Result 只信任 Snapshot。重新编辑统一经 singleDraftFromConfig / jointDraftFromConfig 建立新 Draft 与新 runtime。restoreConfig 仅为执行该转换的 store command，只读摘要不得触发 restore。

### Draft 生命周期与未生效编辑值

保持核心原则：**Draft 只存在于 Conditions。**

例如 Joint Food 在当前 Conditions 会话内切换 `shared ↔ independent` 时，可以保留另一侧尚未生效的 Food 值；但一旦 `compileDraft()` 开始搜索，Draft 销毁，未进入 Snapshot 的隐藏值不要求跨搜索保留。

因此 round-trip 应理解为：

```text
draftFromConfig(compileDraft(draft))
≈ normalizeCompiledDraft(draft)
```

而不是必须恢复所有仅编辑期存在的隐藏值。

## Scope / Feature 读取方式

### JobConditionScope

Single 与 Joint job 的 per-job 条件语义一致，使用 scope 适配不同 store path：

```tsx
<SingleJobConditionScope>
  <JobConditionEditor />
</SingleJobConditionScope>

<JointJobConditionScope jobId={jobId}>
  <JobConditionEditor />
</JointJobConditionScope>
```

组件：

```tsx
<SearchRangeSection />
<GcdSection />
<FoodSection />
<TankConditionSection />
```

这些 section 不知道 Single / Joint / jobId。

### EquipmentScope

```ts
type EquipmentScope =
  | { kind: "single" }
  | { kind: "joint-shared" }
  | { kind: "joint-job"; jobId: JobId };
```

能力组件自行通过 hook 获取所需状态 / action，例如：

```ts
useForcedGear()
useAllowedForcedGearSlots()
useExcludedSources()
useExcludedGear()
```

不要做 `useXxxModel()` 后整对象 spread 给组件。

场景 wrapper 决定渲染哪些能力 editor；不支持的 capability 若被误用，开发环境直接报错，不静默返回空数据。


Job editor：

```tsx

  <SearchRangeSection />
  <GcdSection />
  <FoodSection />
```

`JointEditorTarget` 只属于页面局部 UI state，不进 Draft / store。

## Conditions / Progress / Result 条件摘要

- Conditions：直接读 live Draft。
- Progress / Result：`snapshot → draftFromConfig()` 后进入只读 scope，复用同一摘要 selector / formatter / component。
- 不要维护两套 Draft summary / Snapshot summary 逻辑。
- 只读摘要复用 Draft 语义，但不复用完整编辑器。

Progress 右栏 **只显示冻结条件摘要**；solver、候选数、gap、nodes、模型信息等全部留 Main。

## Selection / JobSelection

### Single

点击职业立即：

```text
createSingleDraft(jobId) → Conditions
```

### Joint

`JobSelection` 内部继续维护 `Set<JobId>`，不把 selection state 强行提升为受控组件。

但联合模式只负责：

- 选择列表
- 当前选择是否有效
- 无效原因

**“前往条件设置”按钮是否可用、按钮本身、状态文案属于 Selection Screen，不属于 JobSelection。**

建议语义枚举：

```ts
enum JointSelectionInvalidReason {
  TooFewJobs = "too-few-jobs",
  MixedGearGroups = "mixed-gear-groups",
}

interface JointJobSelectionState {
  jobs: readonly JobId[];
  valid: boolean;
  invalidReason?: JointSelectionInvalidReason;
}
```

API 可收紧为两种稳定模式：

```ts
type JobSelectionProps =
  | {
      mode: "single";
      onSelect(jobId: JobId): void;
    }
  | {
      mode: "joint";
      onSelectionChange(state: JointJobSelectionState): void;
    };
```

内部自行决定 single 使用 role grouping，joint 使用 gear grouping；无需暴露 `groupType`。

## Page 与目录所有权

Page 组合 Provider、WorkbenchLayout、Main、Aside，不负责准备大量 props。SidePanel 模板细节见[布局规范](05-布局与样式.md)。

### 页面源码保持平级

目录结构不要按照“稳定 / 实验室”嵌套页面。

```text
ui/
├─ app/
├─ components/
├─ features/
└─ pages/
   ├─ single-workbench/
   ├─ laboratory/
   ├─ joint-workbench/
   └─ gear-comparison/
```

不要：

```text
pages/laboratory/joint-workbench/
```

“属于实验室”只是导航 / 产品发布状态，不代表源码 ownership。

### Page-local 组件归属规则

本次重构同步收紧目录边界：

- 只被某一个页面使用的组件 / store / draft / validation / search orchestration，放在该 `pages/<page>/` 目录下的合适层级。
- 只有被多个独立页面真正共享、且共享的是同一套业务语义与行为时，才提升到顶层 `features/`。
- 纯通用 UI primitive 放 `components/`。
- 组件复杂度、代码行数或“以后可能复用”都不是提升到 `features/` 的理由。

可用下面的判断标准：

> 如果删除某一个 Page 后，该模块就失去独立业务意义，则它应留在这个 Page 目录下。

例如：

```text
pages/single-workbench/components/
  selection/
  conditions/
  progress/
  result/
  summary/

pages/joint-workbench/components/
  selection/
  conditions/
  progress/
  result/
  summary/
```

`SingleResultView`、`JointResultView`、`JointJobSelection`、`JointSharedEquipmentRestrictions` 等 page-specific 组合组件都留在各自页面目录，不再因为“像 feature”就放到顶层 feature。

### 顶层 features 的边界

`features/` 只保留跨页面真正共享的业务能力，例如：

- `job-condition`：Single 与 Joint job 都共享的 SearchRange / GCD / Food / Tank 编辑语义与 scope。
- `search-history`：多个 Workbench 共享的历史记录列表、加载行为、版本确认等通用能力。
- `equipment`：共享 catalog、picker、底层 selector / hook / primitive editor 等；Single / Joint Shared / Joint Job 的具体组合组件仍放各自 Page。

Result / Progress / Selection 等页面级 workflow 不再抽成顶层 feature，除非后续真的出现跨 Page 的一致业务语义。


组件遵守[工程规则](../rules/工程规则.md)的独立目录与相邻 SCSS Modules 约定。上面的目录是职责方向，不要求机械创建全部空目录。JobSelection 的内部 Set 是选择阶段的局部状态，不沿用早期重构中提升为受控列表的假设。

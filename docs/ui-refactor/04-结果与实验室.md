# 结果与实验室

[返回入口](README.md)。来源：[实验室](https://github.com/Yun-Shan/ffxiv-gearing-calc/issues/2#issuecomment-6210358727)、[Comparison](https://github.com/Yun-Shan/ffxiv-gearing-calc/issues/2#issuecomment-6212437647)、[等价替换](https://github.com/Yun-Shan/ffxiv-gearing-calc/issues/2#issuecomment-6212659992)、[导入](https://github.com/Yun-Shan/ffxiv-gearing-calc/issues/2#issuecomment-6212897982)、[最终样式](https://github.com/Yun-Shan/ffxiv-gearing-calc/issues/2#issuecomment-6216126292)。


涉及 domain 结果结构、等价候选计算、固定配装公式或其它 `src/ui` 外修改时，须先提交具体范围与影响供用户确认；UI 阶段先用 mock 完成组件测试，全部 UI 完成后、最终 Playwright 前才提交具体 domain 方案并等待用户确认。本篇仅描述目标契约，见[修改边界](00-冲突与修改边界.md)。
## Single Result UI

Result 主内容尽量适配笔记本高度。

结构：

```text
标题 / 总耗时（弱化 metadata）

四栏核心指标
┌────────────┬────────────┬────────────┬────────────┐
│ 伤害双指标  │ GCD        │ 暴击率      │ 直击率      │
└────────────┴────────────┴────────────┴────────────┘

GearTable
└─ SummaryRow（最终属性）
```

### 四栏规则

第一栏上下显示：

- 每威力伤害期望
- 按 GCD 折算伤害

根据 `snapshot.objective` 高亮真正的优化目标，另一项降权但保留。

第二栏：

- GCD
- Tank 时同栏下方显示坚韧减伤百分比

第三 / 四栏固定：暴击率 / 直击率。

### 最终属性

不再占单独 section，放进 GearTable 最后一行；数据源使用 `result.stats`，不是简单前端求和。

Result 右栏不显示派生效果，改为显示本次条件摘要 + actions。

## Joint Result 最终结构

Result header 后只增加一行 [共享装备] [职业图标 + 职业全称] tabs，不使用缩写，不换行；职业过多仅 tab strip 横向滚动。当前 tab 为 Result 页面局部 state，同时驱动 Main 和 Aside。

- Shared tab：联合结果概览（单职业基线、联合最优、基线保留百分比）与只含实际共享部位的 GearTable，无 CoreMetricBar。不在所有 tab 上方额外放概览。
- Job tab：与 Single 共用 CoreMetricBar + GearTable 主体，展示 shared + private 完整最终配装，最后为最终属性 SummaryRow。共享标记放 slot label 第二行。
- Shared Aside 显示共享条件；Job Aside 显示该职业实际有效条件，包括共享食物与共享来源排除等。切 tab 只更换摘要内容，模板、尺寸、actions/footer 不变。
- Result 删除 proof、分数分子分母、nodes 等搜索过程技术信息；Main Header 不重复放“调整条件”，工作流动作统一放 SidePanel。

## 实验室与路由

顶部导航为“单职业搜索 / 实验室”。/single、/lab、/joint 为平级路由；实验室入口包含多职业搜索与装备对比。gear-comparison 页面源码也与其它页面平级，比较页具体 URL 尚未在来源定稿，不借整理文档擅自锁定。

Joint 属于实验室是导航 metadata，/joint 可表达实验室视觉所属态，但不把 /lab 链接标为 aria-current="page"；该属性仅在实际 /lab 页设置。实验状态不进 Draft、store 或 domain。

## Comparison 输入与来源

先选职业，再添加方案；来源包括 completed History 与配装器分享链接。Single 同职业结果直接适配；Joint 只提取该职业的 jobResult 与实际配置。二者统一为单职业结果快照，Comparison 不依赖完整 OptimizationConfig，不把来源信息带进 GearTable 或数值计算。

历史快照使用保存的结果与 dataVersion，不重新计算。可保留 historyId 或 import URL 作为轻量来源 metadata。第一条添加的方案作为基准。

### 方案基准

History selector 只展示能提取当前职业 completed result 的记录。

第一条添加的方案作为基准；无论来自 History 还是 Import，其它方案都相对该基准展示差异。

第一版不要求 URL 持久化比较组合，也不要求可分享 comparison state。

### Comparison 核心指标

对比页需要直观展示以下差异：

#### 威力 / 伤害

沿用 Result 已经确定的指标语义，不另外创造新指标：

- 每威力伤害期望
- 按 GCD 折算后的伤害指标

相对基准同时显示：

```text
绝对差值
相对百分比差值 = (candidate - baseline) / baseline
```

例如：

```text
每威力伤害
A 128.42
B 129.01   +0.59 / +0.46%
```

#### GCD

直接显示实际 GCD 及相对基准的绝对差值，例如：

```text
A 2.50
B 2.48   -0.02
```

#### 坚韧

仅 Tank 显示坚韧相关差异。

对于减伤百分率，差异优先使用百分点（pp）表达，例如 `+0.22pp`，不要再计算“减伤百分比的百分比变化”。

### 装备差异

装备对比按槽位展示，重点体现：

- 装备本体不同；
- 同一装备但 variant / custom 参数不同；
- 魔晶石不同；
- 最终装备属性不同；
- 食物不同。

对比时完全相同的装备 / 食物不需要每个方案重复一行，而是压缩成一行，并通过该 row 的 marker 表明“全部方案”或具体共享该行的方案集合。

例如：

```text
武器   [A/C] 装备 X ...
       [B]   装备 Y ...

头部   [全部] 装备 Z ...
```

Comparison builder 负责：

```text
按 slot 收集各方案装备
→ 按完整装备语义分组
→ 相同方案合并为一条 row
→ 决定 marker 文案 / row className
→ 传给 GearTable
```

不要让 GearTable 自己理解 comparison、baseline、plan identity 或“为什么这些装备被合并”。

### GearTable 改为 row-driven 展示组件

GearTable 重构为纯展示组件，调用方负责把业务结果适配成 rows。

核心原则：

> GearTable 不知道 Result / Joint / Comparison / 方案 A/B/C 等业务概念，只负责渲染调用方给出的装备行。

建议方向：

```ts
interface GearTableProps {
  rows: readonly GearTableRow[];
}
```

`GearTableRow` 提供该行真正需要展示的数据，以及少量纯展示扩展点，例如：

```ts
interface GearTableRow {
  key: string;

  // 该行左侧显示什么；为空时就留空，不做自动 grouping 协议
  slotLabel?: string;

  item: GearTableItem;

  // 通用展示插槽，GearTable 不理解其业务含义
  marker?: ReactNode;

  // 直接应用到该逻辑行 <tr>
  className?: string;
}
```

其中 `item` 可以通过判别联合表示 gear / food / total 等不同 row 数据。

#### 普通 Result

Result adapter 生成与当前 GearTable 等价的 rows：

```text
OptimizationResult + Config
→ buildResultGearTableRows(...)
→ GearTable
```

#### Comparison

Comparison adapter 生成压缩 / 标记后的 rows：

```text
ComparisonEntries
→ buildComparisonGearTableRows(...)
→ GearTable
```

Comparison 可以自行决定：

- `slotLabel` 哪一行显示；
- marker 显示 `A` / `B` / `A/C` / `全部`；
- 哪些 row 使用 Comparison 页面自己的 CSS `className`；
- 完全相同的 row 是否弱化；
- 同槽位多个不同方案 row 如何排序。

这些都不要转化成 GearTable 内部的 `comparisonMode`、`plans`、`difference`、`appearance`、`groupPosition` 等业务/枚举字段。

### Stat columns 由 GearTable 自行派生

调用方不传 `statColumns`。

GearTable 根据所有传入 rows 中实际存在的 stat 自动收集列，并按统一显示规则排序。

```text
rows
→ collect existing stats
→ 去重
→ 按统一 stat display order 排序
→ render columns
```

这样 Single / Joint / Comparison 都共享同一列推导逻辑，页面不重复维护列定义。

### className 的使用边界

允许每个 `GearTableRow` 直接传 `className`，用于调用方控制该 row 的视觉表现。

约束：

- `row.className` 只作用于该行 `<tr>`。
- 不进一步扩散成 `slotClassName` / `meldClassName` / `statClassNames` 等大量细粒度样式 API。
- 如果未来确实需要 cell 级扩展，再按真实需求增加，不提前设计。

这样 GearTable 不需要枚举 `normal / muted / highlight / comparison / baseline / shared` 等样式语义，也不会被 Comparison 需求侵入。

### dataVersion

继续沿用 Search History 已确定的历史事实语义：

- 不同 `dataVersion` 的历史结果允许一起比较；
- 不使用当前游戏数据重新计算旧结果；
- 若所选方案跨 dataVersion，Comparison 页面显示明显版本提示。

### 本轮不处理

以下内容暂不纳入该 Comparison 第一版：

- 手工创建 / 编辑待比较配装；
- 自动判断“哪套最好”；
- comparison state 分享 / URL 持久化；
- 多职业之间直接互相比数值；
- 任何需要修改 domain 搜索算法的功能。


## 同步 Single 的同属性替换

### 适用范围

第一版仅用于：

```text
Single Search
+ 存在 syncItemLevel / syncLevel
```

Joint 暂不支持；无同步的 Single 暂不计算替换候选。

Domain 在搜索完成时直接把可替换装备列表放进 `OptimizationResult`。UI 不负责重新查询、推导或验证“为什么这些装备等价”。

### Result 直接携带替换候选

建议结果结构提供按槽位的等价候选，例如概念上：

```ts
interface OptimizationResult {
  gear: Gear[];
  // ...
  equivalentGear?: Partial<Record<GearSlot, readonly Gear[]>>;
}
```

当前选中的装备不重复放进该槽位自己的 replacement list。

例如：

```text
weapon selected = A
weapon replacements = [B, C]
```

具体 domain 如何生成 `[B, C]` 后续另行设计。

### Result 页替换语义

用户在 Result 页从 replacement popover 选择 B 后，直接更新当前 Workbench Result：

```text
before:
selected = A
replacements = [B, C]

after choose B:
selected = B
replacements = [A, C]
```

也就是说：

- 新装备成为 `result.gear` 该槽位当前装备；
- 原装备进入该槽位 replacement list；
- replacement list 与当前选中装备必须作为一个原子 state command 一起更新；
- `snapshot: OptimizationConfig` 不变；
- 不重新搜索；
- 不改变搜索耗时、objective、stats 等同属性结果语义。

实现上仍使用不可变 state 更新，不直接原地 mutation React/store 对象。可以提供类似：

```ts
replaceEquivalentGear(slot, replacementKey)
```

的 Result command。

### GearTable 提供通用 replacement 展示能力

延续之前 row-driven `GearTable` 的原则：GearTable 不知道 Single、sync、等价算法等业务语义，只知道某条 gear row 可选携带替换项。

Gear row 可以增加类似：

```ts
interface GearTableGearRow {
  key: string;
  slotLabel?: string;
  item: GearTableGearItem;
  marker?: ReactNode;
  className?: string;

  replacements?: readonly GearTableGearItem[];
  onReplacementSelect?: (item: GearTableGearItem) => void;
}
```

存在 replacement 时，该行显示类似：

```text
[可替换 2]
```

点击后打开 Popover，列出替换装备；选择后调用 callback，由调用方更新 Result。

GearTable 不维护当前选中状态，也不自己交换 replacement list。

### Replacement Popover

Popover 第一版只展示区分候选需要的信息，例如：

- 装备名称；
- 品级；
- 来源；
- 必要时魔晶石 / 其他用于区分同名候选的信息。

因为候选在 domain 语义上已经是等价替换，不需要在弹窗重复展示完整相同属性比较。

选择后关闭 Popover，当前 GearTable row 立即显示新装备，旧装备可在下一次打开 Popover 时选回。

### History 同步更新

与之前“Result 页替换不回写 History”的设想不同，最终规则改为：

> 等价替换视为同一个搜索结果在等价表示之间切换。用户在 Result 页替换后，当前 Search History 记录中的 result payload 同步更新，看起来就像搜索最初直接算出了当前选择的这件装备。

因此：

```text
Result 当前选中装备变化
→ 更新当前 history record 的 result
```

但搜索记录本身不发生新的生命周期事件：

- 不创建新 History record；
- 不修改 `startedAtISO`；
- 不修改 `finishedAtISO`；
- 不修改搜索 duration；
- 不修改 `dataVersion`；
- 不增加 `updatedAt` / replacement timestamp；
- 不记录“原来选了哪件 / 什么时候换的”等操作历史。

History 重新打开后，直接看到最后一次选择后的装备与 replacement list。

如果对应 History record 当初因为 persistence failure 没有成功创建，则 Result 替换仍然正常生效，只是没有记录可更新；History 更新失败同样沿用既定规则：不阻断 UI，只弹 warning toast。

### History 语义修正

之前将 completed history result 描述为完全不可变的“搜索 settle 时历史事实”。该说法在等价替换功能下需要收窄：

- 搜索条件、搜索时刻、耗时、dataVersion 等仍然是不可变历史事实；
- result 中属于同一个 domain 等价解集合的“当前选中装备 + replacement list”允许在 Result 页交换并回写同一历史记录；
- 不把这种交换视为重新计算或新的搜索。


## 导入分享链接与完整导出

### Comparison 增加第二种方案来源

装备对比仍然先选择职业，然后添加要参与比较的方案。方案来源包括：

```text
添加方案
├─ 从历史记录选择
└─ 导入配装器链接
```

History 与 Import 在进入 Comparison 后统一转换成同一种单职业结果快照，再走现有指标/装备差异比较逻辑。

建议 Comparison 不依赖完整 `OptimizationConfig`，而依赖真正用于比较的结果快照，例如概念上：

```ts
interface GearsetResultSnapshot {
  jobId: JobId;
  dataVersion: string; // 每项方案自带版本，History 保留原版本，Import 使用当前版本
  calculationLevel: number;
  syncItemLevel?: number;

  gear: readonly Gear[];
  food?: Food;
  stats: Stats;
  effects: OptimizationEffects;

  damagePerPotency: number;
  damagePerSecond: number;
}
```

History source 与 imported source 分别适配到该结构。

### 导入配装链接的语义

导入链接代表一套已经确定的完整配装，不是一次搜索条件，也不需要伪造 Search History / Search Controller 生命周期。

```text
分享链接
→ 解析完整配装
→ 使用当前项目数据与 domain 计算派生结果
→ 生成只读 GearsetResultSnapshot
→ 加入当前 Comparison
```

导入本身：

- 不运行装备搜索；
- 不生成 Search History record；
- 不伪造搜索耗时；
- 不提供“编辑搜索条件”；
- 第一版不要求刷新后持久化 imported entries；
- 第一版不计算等价替换列表。

具体固定配装的 domain 计算如何复用现有公式链，本轮不展开。

### 职业一致性

Comparison 仍然维持“单职业比较”。

用户已经选择比较职业后，导入链接解析出的职业必须一致：

```text
selected job = PLD
imported job = PLD → 接受
imported job = WAR → 拒绝并提示
```

不要因为导入链接自动切换 Comparison 当前职业，否则会隐式使已选择的历史方案失效。

### 分享格式能力与 Food

Asvel 当前分享格式能够承载完整配装所需信息，包含职业、职业等级、同步品级、装备、魔晶石/自定义属性，并能够通过 gear entry 表达 food。

因此：

- 导入配装链接时直接解析 food；
- 不额外要求用户在导入后手选 food；
- 不做“默认无食物 + 补选食物”的兼容流程；
- 不需要考虑旧链接兼容分支。

Issue 记录当时的 Result → Asvel 分享链接未包含 food，此项作为待核实并修复的导出缺陷；后续重构分享能力时一并修正，使新生成的分享链接包含完整配装（包括 food）。

### dataVersion

Imported snapshot 使用**当前项目数据版本**：

```text
imported link
→ current item/game data
→ current domain formulas
→ current dataVersion
```

History entry 仍使用保存时的 `dataVersion`。

因此 History 与 Import 跨版本比较时，继续沿用 Comparison 已确定的版本提示机制。

### Comparison source metadata

可以保留轻量来源信息用于 UI 标签/操作：

```ts
type ComparisonEntrySource =
  | { kind: "history"; historyId: string }
  | { kind: "import"; url: string };
```

但来源信息不应侵入指标计算或 GearTable；Comparison 的实际比较逻辑只消费统一后的结果快照。


## GearTable 最终视觉补充

以完整旧 SingleJobGearTable 的紧凑语义 table 为基线，删除 div/grid 表格及 compact 双实现。marker 放 slot label 第二行；替换按钮紧靠装备名称右侧，不增加 action 列。总属性使用普通 SummaryRow，允许对比多个方案分别插入，不绑定 tfoot。stat 列由 rows 实际展示属性取 union、去重并稳定排序；样式评估按最多同时 7 个 stat，不能据此截掉真实数据。

GearTable 只渲染 rows 与回调，不管理当前替换选择，不理解 Single/Joint/Comparison。表格在目标视口内完整 fit，不允许横向滚动。

## 尚需明确的 Comparison 操作与容量

来源未确定方案数量上限、删除基准后的基准选择、主动切换比较职业后如何处理已有方案。不能从“导入职业不匹配时拒绝”推导出这些操作规则。

来源同时要求按槽位展开不同方案，并要求 GearTable 完整 fit、普通内容无滚动；多个方案完全不同会增加行数，目前没有经确认的容量或承载方案。需用户确定这种情况下的页面行为，不能自行截断、分页、加滚动或限制方案数量。

来源也未规定相对差值分母为零的显示方式。应避免输出 NaN/Infinity；具体文案与展示方式在对应实现前确认。上述均为来源未定，不是已批准需求。

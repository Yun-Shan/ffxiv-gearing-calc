## Single Result UI

Result 主内容尽量适配笔记本高度。

结构：

```text
标题 / 总耗时（弱化 metadata）

四栏核心指标
┌────────────┬────────────┬────────────┬────────────┐
│ 伤害双指标  │ GCD        │ 暴击率      │ 直击率      │
└────────────┴────────────┴────────────┴────────────┘

GearTable
└─ SummaryRow（最终属性）
```

### 四栏规则

第一栏上下显示：

- 每威力伤害期望
- 按 GCD 折算伤害

根据 `snapshot.objective` 高亮真正的优化目标，另一项降权但保留。

第二栏：

- GCD
- Tank 时同栏下方显示坚韧减伤百分比

第三 / 四栏固定：暴击率 / 直击率。

### 最终属性

不再占单独 section，放进 GearTable 最后一行；数据源使用 `result.stats`，不是简单前端求和。

Result 右栏不显示派生效果，改为显示本次条件摘要 + actions。

## Joint Result 最终结构

Result header 后只增加一行 [共享装备] [职业图标 + 职业全称] tabs，不使用缩写，不换行；职业过多仅 tab strip 横向滚动。当前 tab 为 Result 页面局部 state，同时驱动 Main 和 Aside。

- Shared tab：联合结果概览（单职业基线、联合最优、基线保留百分比）与只含实际共享部位的 GearTable，无 CoreMetricBar。不在所有 tab 上方额外放概览。
- Job tab：与 Single 共用 CoreMetricBar + GearTable 主体，展示 shared + private 完整最终配装，最后为最终属性 SummaryRow。共享标记放 slot label 第二行。
- Shared Aside 显示共享条件；Job Aside 显示该职业实际有效条件，包括共享食物与共享来源排除等。切 tab 只更换摘要内容，模板、尺寸、actions/footer 不变。
- Result 删除 proof、分数分子分母、nodes 等搜索过程技术信息；Main Header 不重复放“调整条件”，工作流动作统一放 SidePanel。

## 实验室与路由

顶部导航为“单职业搜索 / 实验室”。路由固定为 /single、/lab、/joint、/gear-comparison，页面源码与路由均保持平级；实验室提供多职业搜索与装备对比入口。

/joint 与 /gear-comparison 产品上属于 Laboratory，所属语境由页面自身表达；顶栏 Laboratory 不伪装成当前页面，aria-current="page" 仅在实际 /lab 设置。实验状态不进 Draft、store 或 domain。

## Comparison 输入与来源

先选职业，再添加方案；来源包括 completed History 与配装器分享链接。Single 同职业结果直接适配；Joint 只提取该职业的 jobResult 与实际配置。二者统一为单职业结果快照，Comparison 不依赖完整 OptimizationConfig，不把来源信息带进 GearTable 或数值计算。

历史快照使用保存的结果与 dataVersion，不重新计算。可保留 historyId 或 import URL 作为轻量来源 metadata。第一条添加的方案作为基准。

### 方案基准

History selector 只展示能提取当前职业 completed result 的记录。

第一条添加的方案作为基准；无论来自 History 还是 Import，其它方案都相对该基准展示差异。

第一版不要求 URL 持久化比较组合，也不要求可分享 comparison state。

### Comparison 核心指标

对比页需要直观展示以下差异：

#### 威力 / 伤害

沿用 Result 已经确定的指标语义，不另外创造新指标：

- 每威力伤害期望
- 按 GCD 折算后的伤害指标

相对基准同时显示：

```text
绝对差值
相对百分比差值 = (candidate - baseline) / baseline
```

例如：

```text
每威力伤害
A 128.42
B 129.01   +0.59 / +0.46%
```

#### GCD

直接显示实际 GCD 及相对基准的绝对差值，例如：

```text
A 2.50
B 2.48   -0.02
```

#### 坚韧

仅 Tank 显示坚韧相关差异。

对于减伤百分率，差异优先使用百分点（pp）表达，例如 `+0.22pp`，不要再计算“减伤百分比的百分比变化”。

### 装备差异

装备对比按槽位展示，重点体现：

- 装备本体不同；
- 同一装备但 variant / custom 参数不同；
- 魔晶石不同；
- 最终装备属性不同；
- 食物不同。

对比时完全相同的装备 / 食物不需要每个方案重复一行，而是压缩成一行，并通过该 row 的 marker 表明“全部方案”或具体共享该行的方案集合。

例如：

```text
武器   [A/C] 装备 X ...
       [B]   装备 Y ...

头部   [全部] 装备 Z ...
```

Comparison builder 负责：

```text
按 slot 收集各方案装备
→ 按完整装备语义分组
→ 相同方案合并为一条 row
→ 决定 marker 文案 / row className
→ 传给 GearTable
```

不要让 GearTable 自己理解 comparison、baseline、plan identity 或“为什么这些装备被合并”。

### GearTable 改为 row-driven 展示组件

GearTable 重构为纯展示组件，调用方负责把业务结果适配成 rows。

核心原则：

> GearTable 不知道 Result / Joint / Comparison / 方案 A/B/C 等业务概念，只负责渲染调用方给出的装备行。

建议方向：

```ts
interface GearTableProps {
  rows: readonly GearTableRow[];
}
```

`GearTableRow` 提供该行真正需要展示的数据，以及少量纯展示扩展点，例如：

```ts
interface GearTableRow {
  key: string;

  // 该行左侧显示什么；为空时就留空，不做自动 grouping 协议
  slotLabel?: string;

  item: GearTableItem;

  // 通用展示插槽，GearTable 不理解其业务含义
  marker?: ReactNode;

  // 直接应用到该逻辑行 <tr>
  className?: string;
}
```

其中 `item` 可以通过判别联合表示 gear / food / total 等不同 row 数据。

#### 普通 Result

Result adapter 生成与当前 GearTable 等价的 rows：

```text
OptimizationResult + Config
→ buildResultGearTableRows(...)
→ GearTable
```

#### Comparison

Comparison adapter 生成压缩 / 标记后的 rows：

```text
ComparisonEntries
→ buildComparisonGearTableRows(...)
→ GearTable
```

Comparison 可以自行决定：

- `slotLabel` 哪一行显示；
- marker 显示 `A` / `B` / `A/C` / `全部`；
- 哪些 row 使用 Comparison 页面自己的 CSS `className`；
- 完全相同的 row 是否弱化；
- 同槽位多个不同方案 row 如何排序。

这些都不要转化成 GearTable 内部的 `comparisonMode`、`plans`、`difference`、`appearance`、`groupPosition` 等业务/枚举字段。

### Stat columns 由 GearTable 自行派生

调用方不传 `statColumns`。

GearTable 根据所有传入 rows 中实际存在的 stat 自动收集列，并按统一显示规则排序。

```text
rows
→ collect existing stats
→ 去重
→ 按统一 stat display order 排序
→ render columns
```

这样 Single / Joint / Comparison 都共享同一列推导逻辑，页面不重复维护列定义。

### className 的使用边界

允许每个 `GearTableRow` 直接传 `className`，用于调用方控制该 row 的视觉表现。

约束：

- `row.className` 只作用于该行 `<tr>`。
- 不进一步扩散成 `slotClassName` / `meldClassName` / `statClassNames` 等大量细粒度样式 API。
- 如果未来确实需要 cell 级扩展，再按真实需求增加，不提前设计。

这样 GearTable 不需要枚举 `normal / muted / highlight / comparison / baseline / shared` 等样式语义，也不会被 Comparison 需求侵入。

### dataVersion

继续沿用 Search History 已确定的历史事实语义：

- 不同 `dataVersion` 的历史结果允许一起比较；
- 不使用当前游戏数据重新计算旧结果；
- 若所选方案跨 dataVersion，Comparison 页面显示明显版本提示。

### 本轮不处理

以下内容暂不纳入该 Comparison 第一版：

- 手工创建 / 编辑待比较配装；
- 自动判断“哪套最好”；
- comparison state 分享 / URL 持久化；
- 多职业之间直接互相比数值；
- 任何需要修改 domain 搜索算法的功能。


## 同步 Single 的同属性替换

### 适用范围

第一版仅用于：

```text
Single Search
+ 存在 syncItemLevel / syncLevel
```

Joint 暂不支持；无同步的 Single 暂不计算替换候选。

Domain 在搜索完成时直接把可替换装备列表放进 `OptimizationResult`。UI 不负责重新查询、推导或验证“为什么这些装备等价”。

### Result 通过 key 引用完整替换数组

用户后续确认覆盖原先“不包含当前项、选择后交换数组”的规则。领域结果集中保存 `equivalentGear: Record<string, readonly MeldedGear[]>`；每个已选装备槽位通过 `replacementGroupKey` 引用完整候选数组。戒指再通过 `uniqueReplacementGroupKey` 引用独立的唯一戒指数组，主数组包含全部普通及唯一戒指；唯一数组只是主数组的唯一戒指子集，用于冲突判断，不作为列表来源。

完整替换池只有一个完整装备方案时，不生成该槽位的替换数组或任何替换 key，UI 不显示按钮；戒指数量只按完整主数组计算，不能把唯一子集重复计数。存在多个方案时，数组包含当前选中项；相同候选集合复用同一个 key。戒指数组中的物理槽位统一为 `ring`，UI 按实际的 `ring` / `ring2` 槽位适配。所有替换数组按品级升序、同品级按物品 ID 数值升序排列；UI 直接按完整主数组展示，不合并唯一子集。

Domain 使用对应装备类型的最终生效属性逐项完全相同判定，包含物理/魔法武器性能及攻击间隔；未提供的零属性与显式零视为相同。候选须满足原搜索范围、职业可穿戴性、来源/装备排除和该槽位强制 ID。镶嵌和自定义参数作为完整方案保存，不只返回裸装备。

候选在正式同步 Single 求解成功后，从合法、未经过 Pareto 剪枝的原始候选池收集，不改变求解器、目标或可行域。义军武器只反推目标属性对应的合法整数分配，不枚举全部分配空间。Joint 和未同步 Single 不生成替换数组。

### Result 页替换语义

```text
before: selected = A, group = [A, B, C]
after choose B: selected = B, group = [A, B, C]
```

只不可变更新 `result.gear` 对应槽位，保留该槽位的数组 key；替换数组不改写。搜索配置、总属性、食物效果、指标、耗时和其它搜索事实保持不变，不重新搜索。

UI 将当前项保留在 Popover 内并显示选中样式。对于戒指，如果另一槽位已选中同物品 ID 的唯一戒指，对应候选仍显示但禁用；不同镶嵌/参数方案也不能绕过同物品唯一性。普通戒指允许两槽选择同一物品。Result command 同时拒绝唯一冲突，防止绕过按钮禁用状态。

### GearTable 提供通用 replacement 展示能力

延续之前 row-driven `GearTable` 的原则：GearTable 不知道 Single、sync、等价算法等业务语义，只知道某条 gear row 可选携带替换项。

Gear row 可以增加类似：

```ts
interface GearTableGearRow {
  key: string;
  slotLabel?: string;
  item: GearTableGearItem;
  marker?: ReactNode;
  className?: string;

  replacements?: readonly GearTableGearItem[];
  onReplacementSelect?: (item: GearTableGearItem) => void;
}
```

存在 replacement 时，该行显示类似：

```text
[可替换 2]
```

替换按钮单独占据装备名称之后的一列，表头文字为空，宽度为 `max-content`。仅表格至少一个槽位有可操作替换列表时插入整列，其它行补空单元格；全部无替换时整列省略。名称列不额外增加 40px。点击后打开 Popover，浮层和选项复用条件页装备选择列表的基础样式与装备行；选择后调用 callback，由调用方更新 Result。

GearTable 按调用方适配的 selected / disabled 状态展示，不管理业务选择，也不改写候选数组。

### Replacement Popover

Popover 与条件页装备选择列表使用同一装备行：部位、图标、名称、来源、品级。禁用候选在名称后显示“唯一性冲突”徽标；选中项保留背景和部位左侧勾。完整镶嵌差异通过悬停提示保留，不增加额外列表说明行。

因为候选在 domain 语义上已经是等价替换，不需要在弹窗重复展示完整相同属性比较。

选择后关闭 Popover，当前 GearTable row 立即显示新装备，旧装备可在下一次打开 Popover 时选回。

### History 同步更新

> 等价替换视为同一个搜索结果在等价表示之间切换。用户在 Result 页替换后，当前 Search History 记录中的 result payload 同步更新，看起来就像搜索最初直接算出了当前选择的这件装备。

因此：

```text
Result 当前选中装备变化
→ 更新当前 history record 的 result
```

但搜索记录本身不发生新的生命周期事件：

- 不创建新 History record；
- 不修改 `startedAtISO`；
- 不修改 `finishedAtISO`；
- 不修改搜索 duration；
- 不修改 `dataVersion`；
- 不增加 `updatedAt` / replacement timestamp；
- 不记录“原来选了哪件 / 什么时候换的”等操作历史。

History 重新打开后，直接看到最后一次选择的装备、槽位 key 及完整替换数组。

如果对应 History record 当初因为 persistence failure 没有成功创建，则 Result 替换仍然正常生效，只是没有记录可更新；History 更新失败同样沿用既定规则：不阻断 UI，只弹 warning toast。

### History 事实边界

Completed History 的不可变事实与可交换等价表示分别定义如下：

- 搜索条件、搜索时刻、耗时、dataVersion 等仍然是不可变历史事实；
- result 中属于同一个 domain 等价解集合的当前选中装备允许在 Result 页切换并回写同一历史记录；完整候选数组保持不变；
- 不把这种交换视为重新计算或新的搜索。


## 导入分享链接与完整导出

### Comparison 增加第二种方案来源

装备对比仍然先选择职业，然后添加要参与比较的方案。方案来源包括：

```text
添加方案
├─ 从历史记录选择
└─ 导入配装器链接
```

History 与 Import 在进入 Comparison 后统一转换成同一种单职业结果快照，再走现有指标/装备差异比较逻辑。

Comparison 不依赖完整 `OptimizationConfig`，只消费参与比较的结果快照：

```ts
interface GearsetResultSnapshot {
  jobId: JobId;
  calculationLevel: number;
  syncItemLevel?: number;

  gear: readonly Gear[];
  food?: Food;
  stats: Stats;
  effects: OptimizationEffects;

  damagePerPotency: number;
  damagePerSecond: number;
}
```

History 与 Import 适配到该 snapshot；provenance 独立保存：

```ts
interface ComparisonEntry {
  snapshot: GearsetResultSnapshot;
  dataVersion: string;
  source: ComparisonEntrySource;
}
```

snapshot 只保存参与指标/装备比较的数据。dataVersion、History id、Import URL 属于来源上下文，不进入 GearTable 或数值计算。

### 导入配装链接的语义

导入链接代表一套已经确定的完整配装，不是一次搜索条件，也不需要伪造 Search History / Search Controller 生命周期。

```text
分享链接
→ 解析完整配装
→ 使用当前项目数据与 domain 计算派生结果
→ 生成只读 GearsetResultSnapshot
→ 加入当前 Comparison
```

导入本身：

- 不运行装备搜索；
- 不生成 Search History record；
- 不伪造搜索耗时；
- 不提供“编辑搜索条件”；
- 第一版不要求刷新后持久化 imported entries；
- 第一版不计算等价替换列表。

固定配装由领域 `calculateFixedGearset` 复用正式属性、食物、伤害及 GCD 公式链计算，使用当前数据并保留合法空孔、低等级镶嵌及自定义参数。完整决定和验证见 [Mock 盘点与真实接入](07-Mock盘点与真实接入.md#m04分享链接的固定配装计算)。

### 职业一致性

Comparison 仍然维持“单职业比较”。

用户已经选择比较职业后，导入链接解析出的职业必须一致：

```text
selected job = PLD
imported job = PLD → 接受
imported job = WAR → 拒绝并提示
```

不要因为导入链接自动切换 Comparison 当前职业，否则会隐式使已选择的历史方案失效。

### 分享格式能力与 Food

Asvel 当前分享格式能够承载完整配装所需信息，包含职业、职业等级、同步品级、装备、魔晶石/自定义属性，并能够通过 gear entry 表达 food。

因此：

- 导入配装链接时直接解析 food；
- 不额外要求用户在导入后手选 food；
- 不做“默认无食物 + 补选食物”的兼容流程；
- 不需要考虑旧链接兼容分支。

Result → Asvel 分享 payload 缺少 food 是已确认缺陷。分享能力必须生成包含 food 的完整固定配装链接。

### dataVersion

Imported snapshot 使用**当前项目数据版本**：

```text
imported link
→ current item/game data
→ current domain formulas
→ current dataVersion
```

History entry 仍使用保存时的 `dataVersion`。

因此 History 与 Import 跨版本比较时，继续沿用 Comparison 已确定的版本提示机制。

### Comparison source metadata

来源信息用于 UI 标签/操作，独立于数值快照保存：

```ts
type ComparisonEntrySource =
  | { kind: "history"; historyId: string }
  | { kind: "import"; url: string };
```

但来源信息不应侵入指标计算或 GearTable；Comparison 的实际比较逻辑只消费统一后的结果快照。


## GearTable 最终视觉补充

以完整旧 SingleJobGearTable 的紧凑语义 table 为基线，删除 div/grid 表格及 compact 双实现。marker 放 slot label 第二行；替换按钮位于名称后的可选空表头列，使用 `max-content`；整表无替换时省略此列。总属性使用普通 SummaryRow，允许对比多个方案分别插入，不绑定 tfoot。stat 列由 rows 实际展示属性取 union、去重并稳定排序；样式评估按最多同时 7 个 stat，不能据此截掉真实数据。

GearTable 只渲染 rows 与回调，不管理当前替换选择，不理解 Single/Joint/Comparison。表格继承父容器可用高度；Comparison 装备表允许滚动查看全部行列，不以四方案同时完整 fit 作为通过条件。

## Comparison 容量与操作

第一版最多同时比较 4 个方案，达到上限后禁止继续添加并提示上限。用户已确认装备对比允许滚动，滚动由装备表区域承载，保留当前实现。四方案极端容量不再要求全部行同时显示；所有行列可通过表格滚动访问，不分页、不截断数据或隐藏行。该决定替代原先“完整 fit、禁止滚动、容量暂留”的要求。

第一条添加的方案为 baseline。删除非 baseline 不影响 baseline；删除 baseline 后，剩余顺序最靠前的一项自动成为新 baseline。只剩一个方案仍可保留，但没有跨方案相对差；删除最后一个方案回到空状态。

没有方案时直接切换职业。有至少一个方案时切换职业必须确认；确认后清空全部 entries，再切换 selectedJob。不重新解释 History、不提取 Joint 的其它职业，不保留 Import 再解析。导入职业不匹配仍直接拒绝，不自动切职业。

History/Import adapter 在加入 entries 前验证关键伤害比较指标；为 0 或非有限值等明显无效结果禁止加入。Comparison 内 baseline 分母必须有效，不设 0 → —、Infinity 或 NaN 的展示分支。

# 搜索与历史

[返回入口](README.md)。来源：[正文](https://github.com/Yun-Shan/ffxiv-gearing-calc/issues/2)、[最终设计补充](https://github.com/Yun-Shan/ffxiv-gearing-calc/issues/2#issuecomment-6210161797)、[样式约束](https://github.com/Yun-Shan/ffxiv-gearing-calc/issues/2#issuecomment-6216126292)。

## Search Controller

Store 只保存同步 UI state；异步执行由 controller 管理。

```text
validate latest Draft/runtime → compile + freeze Snapshot
  → 建立 run identity / AbortController / startedAt
  ├─ UI 主路径：optimize → 实际 settle → Result / 新 Conditions
  └─ 非阻断历史旁路：start → 获取 id 后按实际 settle outcome finish
```

历史旁路不得让 optimize 或 phase transition 等待数据库；start 未完成而搜索先 settle 时，旁路保存 outcome，待成功取得 id 后再 finish。start 失败则不 finish。该协调属于 controller/service，不写入可变 Draft。

AbortController 不进 store。Controller 与 Workbench Provider 同寿命，避免多个组件调用 hook 后各自拥有不同 controller。

建议 run identity 防止取消 A 后启动 B 时，A 的迟到 callback 污染 B。

Progress adapter 将 domain callback (`onProgress` / `onCandidateCounts` / `onSolverProgress`) 转成 UI progress state，尽量写成纯 reducer。

Search 成功进入 Result 后，Progress state 生命周期结束；Result 不保留或总结 solver 过程。

## Result 状态与总耗时

Result：

```ts
type SingleResultState = {
  phase: "result";
  snapshot: OptimizationConfig;
  result: OptimizationResult;
  durationMs: number;
};
// Joint 单独使用 JointOptimizationConfig + JointOptimizationResult，不能交叉配对。
```

上面只示意 phase 的核心业务载荷。还需保留展示来源上下文（本次搜索或载入历史的 dataVersion、可选 historyId），新搜索在开始时捕获当次 dataVersion，载入历史时恢复记录自己的 dataVersion/historyId，不能用 currentDataVersion 替代旧记录，以正确展示旧结果并回写同一记录；该上下文不属于用户可编辑 Draft，也不属于求解进度。History.start 迟到返回的 id 要绑定原 run，不能错误关联当前页面结果。具体元数据承载位置可在 UI 实现时选择，不改变原记录版本。

不再需要 `stale` / `attempted` / `failed` / `statusMessage` 等 Result props。

`durationMs` 定义为：

> 用户开始搜索 → 搜索任务实际 settle 的 wall-clock 总耗时。

History 的 `finishedAtISO` 也应使用同一个实际 settle 时间，而不是 IndexedDB 写入完成时间，确保 Result 页耗时与 History 耗时一致。

### Cancel / failed / no-result

三类非成功 outcome 都统一从执行 Snapshot 重建全新 Conditions：

```text
Progress(snapshot)
  ├─ cancelled
  ├─ no-result
  └─ failed
       ↓
draftFromConfig(snapshot)
       ↓
Conditions(new Draft + new EditorRuntime)
```

不要恢复旧 Draft / 旧 GCD analysis runtime。

搜索反馈不进入 Conditions state。改为 Workbench-level 右上角可关闭 Toast：

- cancelled → info
- no-result → warning
- failed → error
- history persistence failure → warning/error

Toast 是 transient UI，不进入业务 store。

用户点“取消搜索”后等待实际 run settle 再执行正常恢复；导航导致的 abort 则先解除 active run 的 UI ownership，再 abort，迟到 callback / finally 不得覆盖目标页面。

### History：dataVersion

`dataVersion` 表示本次搜索使用的游戏数据版本，不作为“历史结果能不能查看”的兼容开关。

#### 查看结果

```text
completed + result
→ 无论当前 dataVersion 是否变化，都允许查看
```

历史 Result 按记录中的 snapshot/result/dataVersion 展示，不拿当前数据重新计算。

#### 编辑条件

```text
record.dataVersion === currentDataVersion
→ 直接载入 Conditions

record.dataVersion !== currentDataVersion
→ Modal Dialog 提示版本变化
→ 用户确认后再进入 Conditions
```

Modal 应明确说明重新搜索会使用当前游戏数据，结果可能不同。

当前阶段无需考虑装备 ID 因版本变化而删除，也无需提前设计 history schema version / migration；真正 schema 改变时再处理。

### History persistence 是非阻断旁路

History 读写失败不得改变搜索本身的业务结果。

- `history.start()` 失败 → Toast，搜索继续；本次没有 history id 即不再尝试 finish。
- `history.complete/cancel/fail/no-result` 更新失败 → Result / Conditions 正常流转，只 Toast。
- Result `durationMs` / History `finishedAtISO` 按搜索任务实际 settle 时间确定，不包含 IndexedDB 写入耗时。

Search 不应等待 history persistence 才进入 Result / Conditions。

### Progress 中的 Search History / Advanced Settings

Progress 期间：

- 允许打开 Search History 并浏览。
- 允许打开 Advanced Settings；当前为空，不额外定义边界行为，未来有实际设置项时再逐项设计。

从 History 执行“编辑条件 / 查看结果”等会替换当前 Workbench 的动作时：

1. 若点击时正在 Progress，弹 Modal Dialog，说明继续会取消当前搜索并载入所选记录。
2. Modal 是阻塞交互，期间用户不能在背后启动新的搜索。
3. 用户确认后**重新读取当前 Workbench state**：
   - 仍是 Progress → 先解除 run UI ownership、cancel 当前搜索，再加载 History；
   - 搜索已经自行完成并进入 Result / Conditions → 不再 cancel，直接加载 History。

必须做确认后的二次状态读取，因为用户停留在 Modal 的时间不确定，原搜索可能已经完成。

## History 承载与列表

Selection 中职业选择下方直接放 History，占 Main 剩余高度。Conditions/Progress/Result 由 SidePanel Footer 的“搜索记录”入口打开真正 overlay，浏览不改变 phase、不自动取消搜索。Footer 同时有“高级设置”空 action，暂不定义尚不存在的设置项。

两种宿主共用同一 SearchHistory 内容与 record 样式，不提供 compact/comfortable/inline/overlay 视觉变体。删除旧 details、defaultOpen、hideSummary 双用途结构。宿主确定高度；overlay header 固定，仅 record list 纵向滚动。

IndexedDB 一次读取所有记录，UI 使用容器内 IntersectionObserver sentinel 增加 visibleCount、渐进挂载；不做数据库分页和上一页/下一页。

record 显示职业与状态、必要条件摘要、开始时间与耗时、编辑条件/查看结果动作；失败详情不能无限撑高条目。Single 摘要可显示品级/GCD，Joint 可显示职业数/共享部位数；示例不得变成运行默认值。

## 加载动作与时间

- 编辑条件：record.config → draftFromConfig → Conditions（新 runtime）。
- 查看结果：仅 completed + result，加载保存的 config/result 与由时间戳派生的 duration → Result。
- History 耗时只由 finishedAtISO − startedAtISO 派生，不再重复存 durationMs。
- Result.durationMs 与 finishedAtISO 使用同一实际 settle 时刻，存储耗时不计入。
- 从 History 载入后需保留对应记录关联，支持[等价替换回写](04-结果与实验室.md)。搜索条件、时刻、耗时、dataVersion 仍为不可变事实；result 的等价表示允许按约定交换。

## 竞态验收

取消 A 再开始 B、导航时 A 迟到 callback/finally、确认历史载入期间搜索自行完成、history.start 尚未写完而搜索已 settle，均不得让过期任务覆盖当前 UI。History 旁路可等待自己的 start 返回后再关联 finish，但 UI 转移不得等待数据库；start 失败后不再 finish。

History 同一记录的 result 写入必须保持用户最后一次选择：先前 complete 或较早替换的慢写入不能覆盖较新等价表示。可在 UI/service 按 historyId 串行化或采用等效内部顺序控制，不增加持久化 updatedAt/替换时间戳。组件/服务测试覆盖连续替换、complete 延迟后替换及写入失败；最终真实浏览器测试重载确认最后表示。该顺序要求是“History 保存最后一次选择”的实现约束，不增加新的搜索生命周期。

# 项目规则与实现记录

本文档记录本项目必须遵守的业务规则、实现过程中已经确认的问题、对应修复方式，以及后续演进的正确方向。目标设计仍以根目录的《自动配装优化项目设计方案.md》为准；本文档描述当前代码的事实状态。

## 1. 数据规则

### 1.1 数据来源优先级

- 生产数据不得手写、随机生成或使用演示回退。
- 游戏资料以对应 MCP 服务器为首选事实来源；能从 MCP 获取的目标版本数据必须使用 MCP。只有确认 MCP 缺少目标 Sheet、字段、行、类型、成员或必要查询能力后，才允许回退到 `https://github.com/Asvel/ffxiv-gearing.git`，并记录缺失项和回退位置。
- FFXIV 游戏数据 Sheet 主要通过 `ffxiv-mcp-lumina` 查询；`Dalamud.*` API 和 `FFXIVClientStructs.*` 底层结构分别通过 `ffxiv-mcp-dalamud-api` 与 `ffxiv-mcp-clientstructs` 查询，三类资料不得混用。
- MCP 与参考项目不一致时，必须核对目标游戏版本、MCP 数据/文档版本和参考仓库 commit。版本一致且 MCP 能覆盖目标资料时以 MCP 为准；版本无法对齐时必须失败或隔离数据，不能静默混合。
- 进入生产数据的 MCP 查询结果必须保存为可复现、可校验的导入产物，并至少记录服务器、Sheet/类型/成员、查询范围、查询或导入时间及可取得的版本信息。参考项目数据必须记录仓库 URL、精确 commit、导入时间和源文件清单。
- 所有来源最终都必须由 `scripts/update-data.mjs` 统一生成 `src/data/generated-data.json`，禁止手工编辑生成文件。
- `scripts/query-mcp-lumina.mjs` 负责启动环境提供的 Lumina MCP stdio 服务器并生成 `src/data/mcp-lumina.snapshot.json`；查询结果不得由聊天文本或手工复制构造。默认查询参考项目中的全部可用装备、战斗食物、职业分类、食物效果、`ItemLevel`、`BaseParam`、`Materia` 和 `MandervilleWeaponEnhance` 行（当前已知的一类自定义参数武器表）。
- `scripts/update-data.mjs` 读取 MCP 快照并优先覆盖参考项目中的同 ID 数据；MCP 未返回的字段或行才保留参考项目值，并在 `dataSources` 中记录缺失范围和回退位置。当前统一更新器仍解析参考仓库的以下原始导出作为补缺和领域常量来源：
  - `data/out/gears-*.js`
  - `data/out/foods.js`
  - `data/out/jobCategories.js`
  - `data/out/levelCaps.js`
  - `data/out/slotCaps.js`
  - `data/out/roleCaps.js`
  - `src/game.ts`
- 当前快照游戏版本和验证版本均为 `2026.08.05.0000.0000`，覆盖 21927 件可用战斗装备、420 种战斗食物、230 个 `ItemLevel` 行、12 个 `BaseParam` 行、1417 个 `Materia` 行及 22 个 `MandervilleWeaponEnhance` 自定义参数武器行。`ItemFood` 行 1800 在该版本动作表中被引用但不存在；参考项目没有把 1800 用作该类食物效果参数，因此它不是必需的食物效果行。导入器只记录该查询缺口，并继续使用同一食物动作中其余 MCP 效果字段，不虚构缺失行。
- MCP 与参考项目均缺少装备、食物、职业、魔晶石或属性上限表时必须直接失败，不能用虚构、近似或内置兜底数据继续运行。
- `ClassJobCategory` 只负责判断装备是否适用于目标职业，必须以实时 `ffxiv-mcp-lumina` 的 `Item.ClassJobCategory` 和对应 `ClassJobCategory` 行作为生产依据；参考项目中的分类映射不再作为该用途的事实来源，也不再要求两边分类 ID、显示文字或职业集合逐项一致。
- 分析 `ClassJobCategory` 等 MCP 数据时，必须实时调用 `ffxiv-mcp-lumina` 的 `describe_sheet`、`get_row` 或 `get_rows`；不得把本地 `mcp-lumina.snapshot.json` 当作 MCP 实时查询结果。实时结果必须记录服务器、Sheet、行 ID、查询范围、游戏版本和查询时间。
- 参考项目的 `jobCategories.js` 仍可用于确定待查询/导入的参考装备 ID，但不能用于覆盖或校验 MCP 的 `ClassJobCategory` 职业适用性。

### 1.2 更新方式

```bash
npm run data:update
node scripts/update-data.mjs --offline
```

默认参考仓库位于 `reference/ffxiv-gearing`。可通过 `FFXIV_GEARING_ROOT` 指向其他本地检出。联网模式执行 fast-forward 更新；离线模式只解析已有检出。

## 2. 属性与战斗规则

### 2.1 基础属性

最终属性不是装备属性的简单总和。计算顺序为：

1. 根据 `jobLevelModifiers` 取得等级基础参数。
2. 使用职业 `statModifiers` 计算主属性和耐力等基础值。
3. 加入族群属性。当前 UI 未提供族群选择，逻辑层默认使用上游索引 0，即“人族 - 中原之民”。
4. 累加装备及实际生效的魔晶石属性。
5. 最后应用食物的百分比加成和固定上限。

以 100 级武士为例，基础力量为：

```text
floor(440 * 112 / 100) + 2 = 494
```

遗漏基础属性会使伤害评分和已知配装产生数量级明显的偏差。

### 2.2 单件装备属性上限

魔晶石必须在单件装备上逐颗应用，不能先汇总全套后统一截断。上限完全复刻参考项目：

```text
cap = round(levelCaps[stat][itemLevelIndex]
            * slotCaps[stat][rawSlot]
            * roleCaps[stat][roleId]
            / 100000)
```

每颗魔晶石应用后的属性值为：

```text
effective = min(cap, current + materiaValue)
```

UI 中的 `+54` 表示魔晶石标称值；实际增加量可能因单件属性上限而小于 54。优化评分必须使用截断后的实际值。

### 2.3 魔晶石等级

- 数值来自上游 `materias`。
- 可用等级来自上游 `materiaGradeRequiredLevels`。
- 根据装备品级选择满足要求的最高等级，禁止写死“十二型”或固定 `+54`。
- 当前搜索只处理装备自带的普通孔，尚未枚举 `materiaAdvanced` 的禁断孔与成功率。

### 2.4 伤害期望

`calculateEffects` 必须与参考项目 `equippedEffects` 的取整顺序一致，尤其包括：

- 暴击率与暴击伤害；
- 信念倍率、直击率、坚韧伤害与减伤；
- 职业主属性修正后的武器伤害；
- 默认 5% 队伍主属性加成，或职业显式提供的 `partyBonus`；
- 职业攻击主属性、特性倍率及 GCD 修正；
- 每一步规定位置的 `floor`，不能把取整统一移到公式末尾。

截图中的 7.55 武士基准已固化为回归测试：STR 6501、CRT 3605、DET 2533、DHT 1847、SKS 420、VIT 7467、武器性能 158，结果约为 101.8633，GCD 为 2.17 秒。

### 2.5 槽位规则

- 骑士使用主手和盾牌两个槽位。
- 其他战斗职业使用组合武器槽位。
- 戒指必须选择两件不同 ID 的装备，内部表示为 `ring` 和 `ring2`。
- 第二戒指读取同一原始槽位 12，但搜索状态必须阻止重复装备 ID。

### 2.6 前端结果展示规则

- 用户可见的固定文案必须使用中文；`GCD` 是唯一保留的业务专有名词，原始装备名称和来源名称可以保留上游语言。
- 属性名称必须使用以下中文映射：力量、灵巧、智力、精神、耐力、暴击、信念、直击、技速、咏速、坚韧、信仰、物理基本性能、魔法基本性能、攻击间隔。
- 指标名称统一使用“每威力伤害期望”，其数值直接来自与参考项目 `equippedEffects.damage` 同取整顺序的 `calculateEffects`。
- 推荐配装、装备逐行属性、食物、配装总属性和约束必须在同一结果页连续展示，不得通过标签页隐藏总属性。
- 每个装备行显示该装备最终实际属性，包括普通孔受单件上限截断后的结果；魔晶石标签显示上游标称数值。
- 装备行的副属性达到单件上限时加粗，判定复刻参考项目 `statHighlights`：只对参考项目标记为可高亮的副属性判断装备未镶嵌原生值是否达到上限，不把“镶嵌后刚好达到上限”误显示为原生满属性。

## 3. 优化搜索规则

当前实现采用 Beam Search：

- 每个槽位先按启发式评分保留最多 24 件装备。
- 每件装备枚举普通孔的所有相关属性组合，按应用上限后的最终属性去重。
- 每层最多保留 500 个部分配装状态。
- 最终阶段应用上游标记为 `best` 且具有 VIT 的战斗食物，再使用完整伤害公式评分。
- GCD、最低坚韧和最大坚韧约束在最终状态上检查。
- `findFeasibleGcds` 是独立的 GCD 可行性查询：它枚举当前真实装备、普通孔魔晶石、食物和戒指去重规则，只按速度与坚韧保留可行状态，不使用伤害评分或 Beam Search。
- GCD 可行性查询按速度保留每个速度对应的最大坚韧，再换算并去重为 GCD 档位；因此它不会把“可能达到的 GCD”误缩减为“最高输出配装的 GCD”。
- GCD 目标存在时，正式优化会按累计技速/咏速保留代表状态，避免普通伤害 Beam 在最终约束检查前丢弃低伤害但满足目标档位的状态；查询出的可行档位必须能够交给正式优化生成同档位结果。
- GCD 目标时，中间状态的伤害排序必须先应用真实食物，再复用完整伤害期望公式；不能用未应用食物的属性排序代替最终评分。明确选择食物时使用该食物；自动食物模式只使用数据中可用的最高品级战斗食物，中间阶段按这些真实食物的最高完整伤害期望排序，同时为会改变职业速度属性的食物独立保留各速度档位代表，最终阶段评估最高品级集合中的全部真实食物。食物的比例封顶会改变 DET、CRT、DHT 的取整档位，未应用食物排序可能丢弃最终伤害更高的状态。
- 锁定装备只约束装备 ID，不约束该装备的普通孔镶嵌方案。主优化和 GCD 可行性查询都必须继续枚举并应用锁定装备的普通孔魔晶石，结果页也必须显示实际选择的魔晶石。
- 技速/咏速必须按职业角色读取：坦克、力量职业和灵巧职业读取 `SKS`，治疗职业和智力职业读取 `SPS`。读取错误会把法系无技速误判为速度 0，产生虚假的 2.55 秒档位。

这是一种性能与质量折中，不是数学意义上的全局最优保证。不得在文案、API 或测试中把它描述为严格全局最优。

### 正确的后续方向

1. 用帕累托支配剪枝替代固定的“每槽 24 件”，避免启发式提前丢失潜在全局最优装备。
2. 将伤害优化也按 GCD 档位组织状态，并以 CRT/DET/DHT/SKS/SPS/TEN/PIE 的有效区间进行动态规划或分支定界。
3. 区分 free、fixed、crucial 镶嵌装备，复用参考项目的联合魔晶石优化思路。
4. 为可证明最优的模式提供独立算法或明确的精度/时间选项。
5. 将大量计算迁入 Web Worker，避免扩大搜索空间后阻塞界面。

## 4. 已遇到的问题

### 4.1 虚构生产数据

早期实现曾包含虚构装备名称、食物、固定魔晶石数值和“所有职业可用”的错误映射。该路径已删除。正确方式是解析上游原始文件，并在数据异常时失败。

### 4.2 忽略属性上限

早期实现使用 `gear.stats + melds` 直接相加，导致优化器在已经接近上限的装备上重复堆同一属性。正确方式是使用品级、原始槽位和角色类别三张上游表逐颗截断。

### 4.3 缺少基础属性和职业修正

早期实现从空属性开始累加装备，并把武器性能直接当作完整武器伤害。结果中武士 STR 少 494，CRT/DHT 等少等级基础值，伤害评分约为正确值的三分之二。正确方式是先构建上游基础属性，并按原公式补入职业武器伤害和队伍加成。

### 4.4 过早裁剪魔晶石方案

早期实现每件装备只保留 5 个局部评分最高的镶嵌方案，容易丢失满足 GCD、食物封顶和整套协同的组合。当前已改为保留全部去重后的普通孔合法组合。

### 4.5 单戒指和盾牌映射错误

早期实现只有一个戒指槽，并把原始槽位 2 的盾牌映射为武器。当前已拆分 `offhand`、`ring` 和 `ring2`。

### 4.6 用固定值掩盖缺失数据

早期伤害公式在没有武器时回退到 140。此类回退会把非法配装伪装为有效结果，已经删除。必需数据不存在时应返回无解或抛出明确错误。

## 多阶段剩减与帕雷优化的数学证明

优化器在任何阶段都不能任意选择“代表性候选”。所有剩减都必须能够用以下数学事实证明不会丢弃全局最优解。

### 阶段一：单位内领先候选剩减（严格）

对于同一部位、同一任务、同一等级范围内的多个装备候选，如果装备 A 在领先维度上全部不弱于装备 B 且至少一项严格严格高于 B，则 A 领先。领先维度包括主属性、CRT、DET、DHT、TEN、武器伤害。有 GCD 目标时还包括速度，且仅同速度组内才可比。

**严格性证明**：假设装备 A 领先装备 B。那么任何含 A 的完整配装，将 A 换成 B 后必然在所有属性上不优于原配装，武器伤害也不增加；而且 GCD 目标下二者同速度，食物加速也一致。因为伤害期望在所有输入上都是单调函数（每项属性限定为 min(原值，封顶)，食物为 min(固定值，floor(乘以比例))，以及 damage 为运算式乘积），领先的 A 保证了伤害期望不降低。所以 A 可以安全取代 B 而不丢失全局最优。

### 阶段二：同一速度组内状态领先剩减（严格）

在达到了同样的装备集合后，如果状态 A 在领先维度上全部不弱于状态 B 且至少一项严格高，则 A 领先 B。不同速度的状态不可比。为了保证可行性，需要结合食物选择。

**严格性证明**：与阶段一同理。同速度组内状态 A 领先 B 保证以 A 为前缀的所有后续配装不会低于以 B 为前缀的同样后续。不同速度组不可比，是因为后续装备与食物可能改变最终 GCD。

### 阶段三：速度食物代表保留

由于每个装备可能被多个不同食物选择决定其最终 GCD，那些会改变业职速度属性的食物需要在各个速度组上保留代表。

**严格性证明**：例如法系食物提供的速度加成会减少 GCD。如果某个速度组内的代表被丢弃，而该速度只能由含该食物的配装达到，则完整最优解会被错过。为每个会改变速度的食物在每个速度组保留代表，可以保证全局最优不被丢弃。

### 帕雷宽度限制：超过限制会放弃全局最优保证

当前代码在中间档位保留最多 2000 个状态。这是一个资源限制，而不是严格剩减。如果全局最优解被这个资源限制剩减，优化器会返回例主准的“高质量近似解”。

为了缓解这个问题，项目提供了 worker 多线程并行计算（见 src/domain/optimizer.worker.ts 与 src/domain/worker-client.ts）。按首个装备槽候选拆分任务后，多个 worker 各自跑完整搜索。由于各子任务状态集互不包含同一装备 ID，子任务中装备不会出现重复，所以逐个子任务内部的全局最优合并后仍为全局最优。

#### 阶段二边界 bug 修复（2026-09）

`expandBeam` 中的 `bySpeed` 必须遍历 `expanded`（全部候选），不能遍历 `ranked`（按 score 排序的前 2000）。原实现以 `ranked` 为源构造同速度档位代表，高 SPS 但 score 较低的状态会被顶层排序提前剪掉，无法被同档位代表重新加入，使“同一速度档位保留多个代表”这层保护名存实亡，违反“不丢全局最优”的承诺。

修复后该函数以 `expanded` 为源遍历，同一速度档位始终保留 up-to-4 代表，BLM 2.45 GCD 这类依赖高 SPS 状态的需求不再被 frontier 丢提；同一函数中的 `speedFoodRepresentatives(expanded, ...)` 本就以 `expanded` 为源，不需调整。

## 自定义参数武器

- 业务定义：装备带 `customizable: true`，且其自定义参数能从已确认的上游参数表读取。当前已知来源包括 `MandervilleWeaponEnhance`，但不能将其当作唯一类型；其他自定义参数武器可能在其他表中，必须分别确认来源后才能接入。
- 生产主键：每个已确认参数表中的有效 Item 主键。参考项目 `customizable: true` 集合仅作为别名溯源记录，不能替代未确认的参数表；不同参数表之间不能因共享字段结构就默认可合并。
- 参数语义：每件武器 4 个 Materia 槽，参数取值由 `Materia[i]`（Materia 行 ID）+ `MateriaBigValueIndex[i]` / `MateriaSmallValueIndex[i]` 决定；候选生成阶段必须按 Materia 行读取实际 stat/value，不得使用 12/24/54 等固定数值。
- 上游可选规则（2026-09 用户确认）：4 个槽位中必须选 1 small + 2 big + 1 空槽，每个槽至多被选一次；候选数 C(4,1) × C(3,2) = 12。旧的"每槽独立 big/small = 16 种"实现已被取代，不得回退。
- 候选生成实现：`src/domain/optimizer.ts` 的 `forEachMeldCombination` 按"先选 1 small、再从剩余 3 槽选 2 big、1 槽留空"生成 meld；若 `customParameters.length !== 4` 显式抛出异常，禁止静默兜底。
- 当前快照样本（MCP 2026.08.05）：`MandervilleWeaponEnhance` 有 51000-51021 共 22 行；参考导出额外保留 15223-15264 等历史别名（仅作为溯源记录，不参与自定义参数候选）。其他类型的自定义参数武器必须等待对应上游表确认。
- 当前已确认参数表缺失或与参考项目别名完全无交集时，导入器必须显式失败；不允许把参考项目 `customizable: true` 装备作为未确认参数表的生产信源。

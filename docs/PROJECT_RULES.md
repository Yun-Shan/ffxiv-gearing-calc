# 项目规则与实现记录

本文档记录本项目必须遵守的业务规则、实现过程中已经确认的问题、对应修复方式，以及后续演进的正确方向。目标设计仍以根目录的《自动配装优化项目设计方案.md》为准；本文档描述当前代码的事实状态。

## 1. 数据规则

### 1.1 数据来源优先级

- 生产数据不得手写、随机生成或使用演示回退。
- 游戏资料以对应 MCP 服务器为首选事实来源；能从 MCP 获取的目标版本数据必须使用 MCP。只有确认 MCP 缺少目标 Sheet、字段、行、类型、成员或必要查询能力后，才允许回退到 `https://github.com/Asvel/ffxiv-gearing.git`，并记录缺失项和回退位置。
- FFXIV 游戏数据 Sheet 主要通过 `ffxiv-mcp-lumina` 查询；`Dalamud.*` API 和 `FFXIVClientStructs.*` 底层结构分别通过 `ffxiv-mcp-dalamud-api` 与 `ffxiv-mcp-clientstructs` 查询，三类资料不得混用。
- MCP 与参考项目不一致时，必须核对目标游戏版本、MCP 数据/文档版本和参考仓库 commit。版本一致且 MCP 能覆盖目标资料时以 MCP 为准；版本无法对齐时必须失败或隔离数据，不能静默混合。
- 进入生产数据的 MCP 查询结果必须保存为可复现、可校验的导入产物，并至少记录服务器、Sheet/类型/成员、查询范围、查询或导入时间及可取得的版本信息。参考项目数据必须记录仓库 URL、精确 commit、导入时间和源文件清单。
- 所有来源最终都必须由 `scripts/update-data.mjs` 统一生成 `src/data/generated-data.bin`，禁止手工编辑生成文件；MCP 查询输入仍保存在 `src/data/mcp-lumina.snapshot.json`。
- 运行时文件遵循[运行时数据二进制格式](运行时数据二进制格式.md)，使用无压缩二进制编码，不在容器中保留 JSON 文本。装备实体按唯一适用主属性物理分组；无法唯一确定的实体进入独立共享组。实体只存一份，物理组内按品级、ID 升序；五组主属性索引合并引用对应组和共享组中适用该主属性的实体，并在初始化时快速解码。装备对象按主属性与品级范围惰性解码，`weaponDamage` 由武器伤害属性恢复。
- 浏览器、优化 Worker 与 Node 数据工具共用解码逻辑。装备字段、逐件来源、主属性索引及其排序在 `scripts/update-data.mjs` 生成阶段校验；运行时检查文件 CRC、容器结构和段边界，并拒绝损坏或不支持的文件，不读取旧 JSON 或内置数据。
- `Item.Name` 为空或仅含空白的物品视为游戏中已移除，导入时排除，不进入装备、食物候选及任何后续计算；不得使用参考项目旧名称恢复该物品。名称字段缺失或格式错误属于数据错误，必须明确失败。
- `scripts/query-mcp-lumina.mjs` 负责启动环境提供的 Lumina MCP stdio 服务器并生成 `src/data/mcp-lumina.snapshot.json`；查询结果不得由聊天文本或手工复制构造。默认查询参考项目中的全部可用装备、战斗食物、职业分类、23 个受支持职业的 `ClassJob` 行、食物效果、`ItemLevel`、`BaseParam`、`Materia` 和 `MandervilleWeaponEnhance` 行（当前已知的一类自定义参数武器表）。职业行须先用 `ClassJob.Abbreviation` 通过 `search_rows` 发现，再以 `get_rows` 批量读取；不得写死或凭记忆录入 row ID。
- 职业原生等级属性修正和职业名称使用 `ClassJob` 的 MCP 字段；职业角色、主副属性、GCD/特性/队伍公式、等级上限及默认品级范围使用参考项目 `src/game.ts` 中对应职业 schema，并按职业记录各字段来源。青魔法师 `BLU` 与驯兽师 `BST` 属于受支持限职，MCP 行用于名称、原生 modifiers、限职和盾牌能力核验，等级上限及默认品级范围来自参考 schema。
- 同步品级所属等级从 MCP `ContentFinderCondition` 的 `ClassJobLevelRequired`、`ItemLevelRequired`、`ItemLevelSync` 生成，转换顺序遵循参考项目 `data/convert.ts`，并与 `data/out/syncLevels.js` 逐项核对。全量行、Schema、版本与查询时间保存在 MCP 快照；同品级多行归属按参考转换的行 ID 顺序覆盖。参考 `src/game.ts` 的 `syncLevelOfJobLevels` 仅提供未列品级的精确等级对应；`ParamGrow.ItemLevelSync` 与该参考映射语义不同，不混用为分组来源。
- 可变等级装备进入候选。MCP `Item.SubStatCategory === 2` 映射为 `equipLevelVariable`；`BaseParam` 55/56 保留为 `main` / `secondary`，在按职业生成候选时分别解析为该职业的主、副属性。等级同步按参考项目 `Gear.syncedLevel`：可变等级装备的目标品级为显式同步品级与 `syncLevelOfJobLevels[配置职业等级]` 的较小值；目标低于装备原品级时按目标品级属性上限封顶并禁用普通魔晶石。单职业、联合搜索和可行 GCD 查询必须采用一致处理。
- 青魔法师每点 INT 对应的魔法武器伤害加值表在 Lumina MCP 的 Sheet 清单和 `ClassJob` 字段中均不存在。只有在当前 MCP 快照保存了 `list_sheets` 与 `ClassJob` 的 `describe_sheet` 结果并确认没有对应表/字段时，才允许从参考项目读取映射；来源文件为 `data/out/bluMdmgAdditions.js`、`data/in/bluMdmgAdditions.txt` 与 `data/convert.ts`。更新器必须逐项校验导出与原始测量文本一致，且所有数值均为非负安全整数，禁止缺失兜底、截短或近似。
- `scripts/update-data.mjs` 读取 MCP 快照并优先覆盖参考项目中的同 ID 数据；MCP 未返回的字段或行才保留参考项目值，并在 `dataSources` 中记录缺失范围和回退位置。当前统一更新器仍解析参考仓库的以下原始导出作为补缺和领域常量来源：
  - `data/out/gears-*.js`
  - `data/out/foods.js`
  - `data/out/jobCategories.js`
  - `data/out/levelCaps.js`
  - `data/out/slotCaps.js`
  - `data/out/roleCaps.js`
  - `src/game.ts`
- 当前快照游戏版本为 `2026.09.15.0000.0000`，服务器验证版本为 `2026.08.05.0000.0000`，版本警告及通用查询可用性声明保存在快照中，覆盖 22023 件可用战斗装备、420 种战斗食物、23 个职业、230 个 `ItemLevel` 行、12 个 `BaseParam` 行、1417 个 `Materia` 行及 62 个 `MandervilleWeaponEnhance` 自定义参数武器行。刷新 `ClassJobCategory` Schema 后，行 30 的 `BST` 字段确认可用且为 `true`；查询、生成和分类解析统一使用同一受支持职业清单，确保该字段进入装备适用集合。`ItemFood` 行 1800 在该版本动作表中被引用但不存在；参考项目没有把 1800 用作该类食物效果参数，因此它不是必需的食物效果行。导入器只记录该查询缺口，并继续使用同一食物动作中其余 MCP 效果字段，不虚构缺失行。
- MCP 与参考项目均缺少装备、食物、职业、魔晶石或属性上限表时必须直接失败，不能用虚构、近似或内置兜底数据继续运行。
- `ClassJobCategory` 只负责判断装备是否适用于目标职业，必须以实时 `ffxiv-mcp-lumina` 的 `Item.ClassJobCategory` 和对应 `ClassJobCategory` 行作为生产依据；参考项目中的分类映射不再作为该用途的事实来源，也不再要求两边分类 ID、显示文字或职业集合逐项一致。
- 分析 `ClassJobCategory`、`ClassJob` 等 MCP 数据时，必须实时调用 `ffxiv-mcp-lumina` 的 `describe_sheet`、`search_rows`、`get_row` 或 `get_rows`；不得把本地 `mcp-lumina.snapshot.json` 当作 MCP 实时查询结果。实时结果必须记录服务器、Sheet、字段、行 ID、查询范围、游戏版本和查询时间。
- 参考项目的 `jobCategories.js` 仍可用于确定待查询/导入的参考装备 ID，但不能用于覆盖或校验 MCP 的 `ClassJobCategory` 职业适用性。

### 1.2 更新方式

通用查询可接受服务器的验证版本滞后，但仅限健康信息明确声明 `get_row` / `get_rows` 等通用工具不受 `GameVersionMismatch` 影响、且没有其他降级原因的情况。必须保存原始警告及可用性声明，导入器再次检查该声明。所有批次采用同一检测游戏版本；便捷接口不适用此例外，也不得将不同版本的快照静默合并。

```bash
npm run data:update
node scripts/update-data.mjs --offline
```

默认参考仓库位于 `reference/ffxiv-gearing`。可通过 `FFXIV_GEARING_ROOT` 指向其他本地检出。联网模式执行 fast-forward 更新；离线模式只解析已有检出。

## 2. 属性与战斗规则

### 2.1 基础属性

最终属性不是装备属性的简单总和。计算顺序为：

1. 先确定计算等级：非同步取当前筛选条件下候选装备中最高品级装备的穿戴等级，并向下取整为十的倍数；同步取参考项目中同步品级所属的等级。再根据 `jobLevelModifiers` 取得等级基础参数。
2. 使用职业 `statModifiers` 计算主属性和耐力等基础值。
3. 加入族群属性。当前默认使用上游索引 0，即“人族 - 中原之民”。
4. 累加装备及实际生效的魔晶石属性。
5. 最后应用食物的百分比加成和固定上限。

以 100 级武士为例，基础力量为：

```text
floor(440 * 112 / 100) + 2 = 494
```

遗漏基础属性会使伤害评分和已知配装产生数量级明显的偏差。

### 2.2 单件装备属性上限

魔晶石必须在单件装备上逐颗应用，不能先汇总全套后统一截断。上限完全复刻参考项目：

```text
cap = round(levelCaps[stat][itemLevelIndex]
            * slotCaps[stat][rawSlot]
            * roleCaps[stat][roleId]
            / 100000)
```

每颗魔晶石应用后的属性值为：

```text
effective = min(cap, current + materiaValue)
```

魔晶石标称值（例如 `+54`）可能高于实际增加量；单件装备属性上限会截断有效值。优化评分必须使用截断后的实际值。

### 2.3 魔晶石等级

- 数值来自上游 `materias`。
- 可用等级来自上游 `materiaGradeRequiredLevels`。
- 根据装备品级选择满足要求的最高等级，禁止写死“十二型”或固定 `+54`。
- 仅生成全部可用孔填满的候选；不可禁忌镶嵌装备填满普通孔，可禁忌镶嵌装备填满五孔，不提供关闭禁忌镶嵌选项；普通孔和首个禁断孔使用最高可用等级，其余禁断孔使用上游允许在限制孔使用的最高等级。限制等级规则由更新器从参考项目导入，不在领域层写死；不优化镶嵌成功率或成本。

### 2.4 伤害期望

`calculateEffects` 必须与参考项目 `equippedEffects` 的取整顺序一致，尤其包括：

- 暴击率与暴击伤害；
- 信念倍率、直击率、坚韧伤害与减伤；
- 职业主属性修正后的武器伤害；
- 默认 5% 队伍主属性加成，或职业显式提供的 `partyBonus`；
- 职业攻击主属性、特性倍率及 GCD 修正；
- 每一步规定位置的 `floor`，不能把取整统一移到公式末尾。

截图中的 7.55 武士基准已固化为回归测试：STR 6501、CRT 3605、DET 2533、DHT 1847、SKS 420、VIT 7467、武器性能 158，结果约为 101.8633，GCD 为 2.17 秒。

### 2.5 槽位规则

- 骑士使用主手和盾牌两个槽位。
- 其他战斗职业使用组合武器槽位。
- 两戒指槽内部表示为 `ring` 和 `ring2`；同 ID 仅在来源明确证明装备不是 unique 时允许。
- 双戒指读取同一原始槽位 12，候选配对必须遵守 unique 装备不能重复、非 unique 装备可以重复的规则。
- 两戒指槽候选身份集合完全相同、没有强制戒指且没有戒指1/戒指2分槽共享约束时，候选生成可折叠仅交换顺序不同的戒指对；任一前提不满足时保留有序候选，结果仍按槽位还原。

## 3. 优化搜索规则

正式算法位于 `src/domain/search`。单职业使用 `findBestLoadoutExactMip`；联合搜索使用 `findBestJointLoadoutV3`，领域适配负责由生成数据构造完整的装备、镶嵌及食物候选。详细设计见 [最优装备算法](最优装备算法.md)，实现证明与数值边界以 [V3 正确性与验收](V3正确性与验收.md) 为准。

- 搜索性能追踪目标按参与职业总数计算，每个职业 30 秒，包括单职业：单职业 30 秒、双职业 60 秒，N 个职业为 `30×N` 秒。它只是进度指标，不改变搜索候选、目标、调用者参数或最优性证明；历史运行保留当时记录的目标口径。

- 不按启发式评分限制每槽装备数量，不设置固定宽度的中间状态截断。装备生成器必须枚举所有已支持的合法普通孔属性方案。规范公式路径构造精确求解候选池时，单职业搜索以及联合搜索中的非共享、非戒指槽位可以流式执行逐槽 Pareto 剪枝，坐标投影必须完整覆盖该职业伤害公式与硬约束：攻击主属性、对应武器伤害、DET、TEN、CRT、DHT 及职业速度；未知或缺失坐标时退回完整属性向量。仅移除被另一候选在全部相关坐标上支配的方案；遇到精确 GCD、多档 GCD 或速度上限时，仅比较速度相同的候选。坐标完全相同的方案保留先生成者。该规则也适用于联合搜索，因为非共享槽位替换不会改变共享身份或戒指跨槽唯一性；共享槽保留完整身份集合，戒指候选继续遵守专用配对与冲突分组逻辑。查询全部可行 GCD 档位的速度可达性路径不执行此剪枝，以保留每个可返回速度档。
- 对单职业和联合搜索中的私有独立戒指槽，可在求解器配对前按跨槽可配对关系执行精确 Pareto：non-unique 与对侧不存在同 ID unique 候选的 unique 候选属于 all-compatible 前沿；all-compatible 候选可在完整属性向量支配时删去任意 unique 冲突组候选。对侧存在同 ID unique 候选的 unique 候选按 item ID 各自成组，只能在同 ID 组内互相支配。冲突组候选不能删除 all-compatible 候选或其他 ID 的冲突候选，因为它的合法配对集合更小。替换必须保留完整相关属性坐标；有 GCD/速度上限时要求速度坐标相同。冲突身份按过滤后的对侧完整候选池计算，戒指 unique 元数据必须完整一致。共享戒指身份池、合并戒指对候选及可达 GCD 查询继续保留完整候选身份，不使用此剪枝。
- 使用 HiGHS 混合整数模型表示装备、食物的离散选择、食物取整及封顶、属性阶梯和约束。以具有误差界的固定点对数组织候选，再用整数伤害因子、BigInt 乘积或有理数复核所有仍可能改善目标的签名。
- HiGHS 若使用 `user_objective_scale`，回调中的 `mip_dual_bound` 以缩放单位返回。任何基于该界的提前终止必须先按同一二进制指数还原到 LP 模型单位，再执行保守取整和 BigInt incumbent 比较；不得把缩放界直接当原目标值。
- 规范职业基线在候选总数达到 2,000 时可启用精确候选乐观上界：以该候选的属性加其他槽逐属性最大值及可行食物加成构造上界，并使用精确整数伤害因子比较；只有被证明严格劣于可行 incumbent 的候选才可移除，相等上界必须保留。该路径不适用于自定义装备属性提取器或最高坚韧模式；初始贪心 MIP hint 最多用 1 秒，上界预处理最多用 10 秒且须为正式求解保留至少 1 秒。达到子预算时保留未扫描候选；取消仍沿统一取消路径中止搜索；不确定时跳过该优化。启用该路径时可同时加入主属性和加权资源支持行；这些行只收紧 MIP 松弛，不替代完整最优性证明。当前 profile 按职业数和已测场景选择：两职业首轮基线和三职业基线禁用候选品级条件资源支持行；VPR+MCH 在 DPS 目标、共享食物与共享耳饰/项链/手镯/戒指对条件下，仅 MCH 基线额外加入主属性和加权资源支持行；RDM+PCT 在 DPS、共享食物和共享防具/常规饰品条件下，仅 PCT 基线加入一条主属性支持行；RPR+SAM 只有在 DPS、共享食物及共享耳饰/项链/手镯与完整戒指对条件下启用主属性支持行和魔晶石补偿（内部把完整戒指对拆成 ring/ring2 时仍按调用者的原始戒指对拓扑判断）；显式共享 ring/ring2 的分槽场景不启用这两项。BRD+DNC+MCH 在共享全非武器装备和食物的 DPS 条件下加入主属性支持行。BRD 单职业、770–795、无同步、DPS、无 GCD/速度/坚韧/强制装备/来源约束时使用 compact 条件资源支持；该设置从 29 行缩减到 11 行，不删候选，精确结果 `50.07705056381793` 且完整证明，Node 最快完整记录为 12.427 秒。两职业固定共享后的受限求解用 compact，每槽最多一条条件资源阈值行；其他常规范围用 compact；四职业及以上且候选总量至少 100,000 时禁用这些行以控制联合模型规模。两条阈值行/槽的 Node 对照未显示稳定收益，已撤回，详见[搜索耗时优化进展](搜索耗时优化进展.md)。profile 不删候选，完整证明要求不变。
- 四职业 BRD+DNC+MCH+VPR、770–795、无同步、独立食物且不共享槽时，基线条件资源支持使用 `compact-weighted`：保留每槽 compact 上界并加历史快照中的加权支持方向；候选集与 exact MIP 最优性证明不变。其他职业数、同步或范围退回通用 profile。
- 候选资源预算的内部 profile 单独按已测条件分流：VPR+MCH、715–795、同步 735、DPS、共享饰品/完整戒指对和共享食物使用 `weighted`；BRD+DNC+MCH+NIN+VPR、715–795、同步 735、DPS、独立食物且无共享槽使用 `uniform-only`；RPR+SAM 730–795 同步 735 的显式戒指分槽，以及 BRD+DNC+MCH+VPR 770–795 无同步独立搜索使用 `disabled`。其余条件使用默认 profile。该策略只加安全候选上界，不裁剪候选；超时或预算耗尽时省略可选上界，仍进行精确完整证明。
- BLM 单职业、730–795、同步 735、`damage`、无 GCD/速度/坚韧/强制装备/来源约束时使用 compact 条件资源支持；该设置从 43 行缩减到 10 行，不删候选，精确结果 `91.6344764121696` 且完整证明，Node 最快完整记录为 3.139 秒、同策略复测 3.204 秒。BRD 单职业 compact profile 的已测条件和结果见上一条策略记录与[搜索验收条件](搜索验收条件与历史最优记录.md)。
- BRD 单职业、770–795、无同步、DPS 且无 GCD/速度/坚韧/强制装备/来源约束时，在 compact 条件资源支持外增加一条安全主属性资源上界行；总模型行数只增加 1，候选不变，结果 `50.07705056381793` 且完整证明，Node 两次为 11.274/11.287 秒。只在该精确输入启用，其他场景继续使用 compact 原策略或其既有 profile。
- RPR+SAM 在 DPS、共享食物与共享饰品/戒指对的候选热启动中，可尝试最多两个私有非戒指槽的同物品合法镶嵌变体，用于恢复单职业最优解的完整原始整数属性向量。只有逐项属性完全相等并再次满足约束、GCD 与戒指 unique 校验时才提交；这只改善 incumbent，不剪候选、不构成上界或最优性证明，随后仍执行完整精确证明。策略只应用于直接种子尝试及已完整枚举且组合数不超过 8 的共享赋值。
- 候选品级条件资源支持把“最高品级下 20 品级、以及同步品级下 20 品级”只当作先验搜索窗口，窗口外装备仍保留。资源使用每个实际装备候选在同步、硬属性和完整魔晶石方案生效后的属性向量，覆盖主属性、武器伤害、DET/TEN/CRT/DHT 与速度；因此额外魔晶石孔或肝武的较大资源值不会被品级单调假设抹去。资源支持只收紧 MIP 松弛，不能将平均斜率、品级差或“基本不会反超”用作候选剪枝证明。
- 基线 worker 可将装备/食物数值列紧凑传输并按原始候选索引还原结果对象；职业结果仍按输入顺序关联。并发限制及取消、截止时间、清理规则见下文，外部搜索参数和结果对象能力不得因 worker 序列化而改变。
- 精确 MIP 构造因子类前，可按属性使用每个槽的完整候选值做精确可达和 DP，再对所有食物应用与整数属性模型相同的取整和封顶公式；可删除完全不可达的因子类，并把保留类的属性区间收紧到可达值端点，同时保留其因子值、对数值和辅助值。共享身份、unique 及其他属性约束可以从 DP 中省略，因为这只会扩大可达集合。武器伤害因子类也可按武器属性最终可达值剪枝；BLU 的武器伤害可达集合必须与主属性因子类的 evaluator 附加值做笛卡尔和。重复食物属性修饰、状态宽度、单槽转换或食物评估超预算、属性范围无效、和溢出或没有类匹配时，必须让该属性轴完整使用原因子类，不得截断 DP 状态后继续剪枝。任何收紧的变量上下界都必须覆盖所有实际可达值。
- 初始可行解和 HiGHS 用户解回调只用于启发式地改进 incumbent；回调结果不构成最优性证明，必须继续完成精确求解、签名穷尽与正式复核后才能返回结果。
- 配置了 worker executor 时，不含自定义装备属性提取器的职业基线、固定共享组合下的职业精确子问题及受限共享种子求解可并发执行；通常最多 4 个 worker，五职业且装备候选总量不超过 13,500 时最多 5 个，大候选（总量达到 100,000）仍最多 3 个，以避免内存密集型模型过度并发。每批任务共用搜索截止时间与取消信号，结果仍按职业索引关联。一次联合搜索内可跨批次复用 worker，空闲 1 秒后释放，并在完成、取消或异常时清理。自定义提取器继续使用顺序求解。完整共享装备/食物组合不超过 8 且候选已完整生成时，可逐一枚举共享组合，并对固定组合下的职业子问题精确求解；只有全部组合完成或达到已证明的全局上界后，才完成外层证明。
- 联合搜索可用逐属性最大值构造共享选择的乐观属性上界；只有所有职业的精确有理数上界之和不超过当前 incumbent 时才排除该选择，无法安全计算上界时必须跳过。共享赋值前缀上界对一般模型最多检查 20,000 个前缀、累计预处理不超过 `min(250ms, maxSearchMs×2%)`；至少四职业且共享赋值域超过 20,000 时，可最多检查 100,000 个前缀、累计预处理不超过 `min(1,500ms, maxSearchMs×2%)`，并最多保留 2,000 条前缀上界行。两个职业且共享赋值组合上界超过 1,000,000 时跳过这类可选前缀 cut：同输入 Node 复测中，最多 20,000 个低收益前缀 cut 使完整不可行证明从约 57 秒增至约 204 秒；其他模型仍按各自预算生成。达到任一预算只停止可选上界生成，已得上界行仍须满足同一精确安全条件，剩余搜索照常完成证明。
- 精确因子对数分数可按装备贡献资源建立 Lagrangian 上界：每个因子类别使用其精确整数 `round(LOG_SCALE × ln(factor))` 分数和达到该分数所需的最小属性贡献；非负资源价格的支持线以 BigInt 构造上界，资源预算覆盖主属性、武器伤害、副属性和速度，并将食物上限与其他槽逐属性最大值作为保守预算。该上界不把主属性替换为近似线性权重；只有对数上界连超过当前联合阈值所需的分数也达不到时，才可禁用对应候选或共享组合。准备超时、输入无效或比较边界不确定时必须保留候选，并继续完整精确证明。四职业及以上共享域不启用候选资源分数 cut 或共享前缀资源分数查询；实测这些查询未产生 cut，却把前缀预处理从原有最多约 100,000 次检查降到约 5,000 次/秒，导致模型没有 80/64 条已有安全前缀 cut。该职业数保留原有精确有理数共享前缀剪枝；少于四职业且确实准备出资源预算时才计算分数上界。
- 候选资源上界可使用多组非负资源价格，分别计算安全支持线并取最小上界；价格只界定资源成本，不得替代精确因子对数分数或把主属性按经验权重线性加入目标。仅当实际候选池包含低于 730 品级的装备时启用额外价格向量；全为 730 及以上的候选池沿用原单价格路径。无此门控的全局试验使 VPR+MCH、730–795、同步 735 搜索耗时升至 77.756 秒，超过 41.229 秒历史最快对应的 45.352 秒验收上限，已回退；门控后的 715–795 宽域 Node 完整证明为 `8673/4337`、86.559 秒，并生成 10 条安全候选上界 cut。仅在严格证明候选无法超过当前 incumbent 时才可剪候选，所有路径仍须完成精确证明。
- 通用装备剪枝后若每个共享槽只剩一个身份选择，联合搜索固定该组合并逐职业精确重优化；所有共享食物仍须枚举。该单组合路径以条件最优上界完成证明，不需要联合因子 MIP。
- 联合 MIP 可按各职业单个因子类别的精确比例上界添加 one-hot 冲突行；因子类别多时还可用同一职业两个不同因子组的 BigInt 有理数上界加强缩放比例变量，也可用正倍率的固定点乘积上界链；该链按职业数设置行预算，并只保留最大化证明所需的安全上界行。三职业及以上可按两个或三个职业因子类别上界之和添加有界聚合冲突行。共享选择的单项、成对及部分赋值前缀上界可用各职业精确有理数和进行剪枝。所有加强行只缩小 MIP 松弛，不得截断候选或跳过完整证明；预处理超出预算时只能跳过可选加强行。
- 对 VPR+MCH、730–795、同步 735，BRD+DNC+MCH+VPR、715–795、同步 735，以及 `BRD+DNC+MCH+VPR`、715–795、同步 735，在 DPS、共享耳饰/项链/手镯/戒指对与食物且没有额外职业约束时，联合因子 MIP 跳过 `joint_ratio_pair_upper_*` 可选成对比例上界行；保留单因子组上界、全部候选、精确 BigInt 目标比较及完整严格证明。该路径只改变松弛强度。四职业宽域完整 Node 结果为 `18973495/4744003`、`proof.complete=true`、85.231 秒；优化结果汇总见[搜索耗时优化总结](search-optimization/搜索耗时优化总结.md)，历史记录见[耗时优化归档](search-optimization/耗时优化记录.7z)。定向模型为 8,325 个变量、1,984 行、328,191 个非零项。VPR+MCH 宽域关闭成对比例行的试验虽得到完整证明和正确结果，但耗时 157.681 秒，超过历史容忍，因此该宽域继续用默认成对上界策略；该策略最新完整证明为 86.559 秒。其他输入继续使用默认策略；VPR+MCH 的 730–795 窄域仍按已验证配置关闭成对行。
- 已有精确联合 incumbent 后，可以用 HiGHS 最大化 MIP 的对偶上界提前结束求解；只有上取整后的整数界经 BigInt 比较不超过 incumbent 时才可证明完成，并在结果中标记 `DualBound`。对偶界限不能支持形式化证书声明。
- 单职业目标支持每威力伤害期望和按 GCD 折算的目标。联合目标为各职业目标值除以各自单独最优基线的比例之和；不能用乘积最优替代比例总和最优。基线与联合模型采用同一目标和各职业约束。
- 多职业联合搜索只接受同组职业：所有防护职业为一组，所有治疗职业为一组，DPS 则按力量、灵巧、智力分别成组。领域入口依据 `jobSchemas[jobId].role` 在候选生成前拒绝跨组组合；坦克与力量 DPS 即使攻击属性都映射为 STR，也不属于同组。
- 各职业独立配置 GCD 单值或离散多值、速度上下界、最低坚韧、最低减伤百分比及最高坚韧。离散 GCD 的速度区间必须保持并集，不得填成包含未选档位的连续区间。
- 最高坚韧先在完整候选集合中求得，再将该值作为联合搜索的硬约束；不能固定共享方案后降低要求。
- 共享部位按名称对齐，包含同一装备及同一完整属性方案。共享戒指1与戒指2可分别选择或同时选择，匹配各自完整装备与镶嵌身份；完整戒指对仍用于校验整套配装的唯一性。完整戒指对未锁定任何戒指位置时，候选生成可直接使用两个独立戒指槽，避免先构造所有有序戒指对；联合搜索要求每个职业两个槽的完整候选身份集合相同、使用各职业共有的全局身份顺序并添加跨槽 `itemId` unique 约束，将正反两个排列约化为一个。该对称约束只适用于默认对称属性提取的完整共享戒指对；热启动在进入模型前归一到同一顺序，结果按原接口还原为两枚戒指。存在强制位置、槽身份不对称或不满足拆分条件时保留原有 pair 候选路径。联合 MIP 对完整 pair 候选的内部拆分也仅在候选域为完整合法笛卡尔积、属性可加且 unique 元数据齐全时启用；共享完整戒指对保持同一无序身份多重集。共享食物取各职业可用食物身份交集，独立食物分别求解。
- 技速/咏速按角色读取：坦克、力量和灵巧职业使用技速，治疗和智力职业使用咏速。可行 GCD 查询与正式求解使用相同候选、食物、镶嵌与硬约束，输出档位必须能正式求解。
- 装备锁定约束装备 ID；锁定装备的普通孔仍参与优化。锁定 ID 缺失或与来源、品级、穿戴等级、排除条件冲突时返回无可行配装，不自动改选其他装备。等级同步先处理装备属性上限，并禁用被同步普通装备的魔晶石；自定义参数武器保留参数分配并按同步上限截断。
- 浏览器搜索在工作线程中执行，支持进度和取消；正式前端搜索不设置搜索时限。工作线程完成异步模块初始化并注册消息监听后发送 `ready`，调用方收到后才发送搜索请求，避免初始化期间丢失请求。取消不得返回未完成的结果。搜索时限只用于测试与 Node 验收入口。运行时缓存有界，不读取预先打表文件。
- 只有求解器报告最优且复核完成才返回结果，无法完成时明确失败，不返回近似配装。最优性限定于输入候选及约束；HiGHS 使用浮点求解，不提供独立形式化有理数证书。
- Node 验收入口的进程 RSS 保护与浏览器能力分别描述；浏览器无法取得进程 RSS，不能把不可用统计伪称为实测内存。
- 正式 Node 联合验收可以通过 `DATA_TEST_V3_TIMEOUT_MS=unlimited` 关闭时间截止，用于测量极端合法输入的完整运行时间；3.5 GiB RSS 保护仍生效。默认时限和普通 UI 搜索边界不变。
- Node 测试与验收包装集中在 `scripts/node-tests`。该目录只放 Node 测试、进程/Worker 启动和结果输出等调用层代码；搜索、候选生成、公式和游戏规则必须复用 `src/domain`，不得在脚本目录实现或复制算法。
- 当前多职业 Node 验收读取经过来源校验的生成数据，并调用 `runJointOptimizationLocally`；它不连接独立 MCP 客户端，也不导入参考项目脚本。
- `scripts/archive` 仅保存旧探索代码、测试记录和日志，不参与构建类型检查、不提供 npm 入口，也不得由生产代码或当前 Node 验收包装调用。需要手动复现历史探索时按该目录内的说明操作。
- 对 `BRD+DNC+MCH+NIN+VPR`、715–795、同步 735、DPS、共享食物与完整共享戒指对/饰品槽的无额外约束精确场景，可在联合 MIP 中对共享耳环、项链、手镯的候选对使用严格跨属性 Pareto 支配 cut。属性向量取自每职业同步封顶和实际魔晶石已应用后的模型属性，并按所有职业展平比较；只有每一维均不低且至少一维严格更高的候选才可支配另一候选。支配候选还须在每个职业中两件装备 ID 不同，且这两个 ID 不出现在该职业其他槽的任何候选中，以保证替换不破坏 unique。该 cut 只排除已被安全替代的共享候选组合；保留原候选属性、食物、其他装备与精确 BigInt 目标复核，HiGHS 仍须完成证明。内部 capability、职业/槽位、目标、共享食物、无投影、规范 evaluator、无自定义属性提取器和无硬约束的底层门控必须同时成立；任何条件不符时禁用该 cut。候选生成、身份映射、调用者选项与结果能力不变。排序和比较共用最多 `min(250ms, maxSearchMs×2%)` 预处理截止及取消检查，预算耗尽时仅保留已证明安全的 cut。
## 4. 正确性约束

- 生产数据必须具有可追溯来源，缺失必需字段时明确失败。
- 装备与魔晶石逐件按上游上限计算，允许最后一颗魔晶石部分生效；不得以局部伤害排名截断候选。
- 基础属性、职业武器伤害修正及队伍主属性加成必须进入正式公式。
- 公式拒绝未支持的等级与缺失的职业主属性、生命值修正，不以其他等级或默认修正替代必需资料。
- 食物百分比以基础属性、装备与实际镶嵌属性的合计计算；整数模型结果必须与领域层计算一致。
- 速度上下界和最低坚韧值指包含基础属性与食物的最终值。最低减伤百分比通过领域公式换算。
- 盾牌使用独立副手槽，双戒指受装备唯一性限制。戒指1与戒指2的共享分别匹配各自装备和镶嵌方案，另一枚戒指仍须满足唯一性。

## 自定义参数武器

- 业务定义：装备带 `customizable: true`，且其自定义参数能从已确认的上游参数表读取。当前已知来源包括 `MandervilleWeaponEnhance`，但不能将其当作唯一类型；其他自定义参数武器可能在其他表中，必须分别确认来源后才能接入。
- 生产主键：每个已确认参数表中的有效 Item 主键。参考项目 `customizable: true` 集合仅作为别名溯源记录，不能替代未确认的参数表；不同参数表之间不能因共享字段结构就默认可合并。
- 参数语义：每件武器 4 个 Materia 槽，参数取值由 `Materia[i]`（Materia 行 ID）+ `MateriaBigValueIndex[i]` / `MateriaSmallValueIndex[i]` 决定；候选生成阶段必须按 Materia 行读取实际 stat/value，不得使用 12/24/54 等固定数值。
- 上游可选规则：4 个槽位中必须选 1 small + 2 big + 1 空槽，每个槽至多被选一次；候选数 C(4,1) × C(3,2) = 12。
- 候选生成实现：领域候选构造器 按"先选 1 small、再从剩余 3 槽选 2 big、1 槽留空"生成 meld；若 `customParameters.length !== 4` 显式抛出异常，禁止静默兜底。
- 当前快照（MCP 2026.09.15）记录 `MandervilleWeaponEnhance` 的 62 个有效参数行，所有 Item 主键与查询范围保存在快照。参考项目的别名只作溯源，不代替 MCP 主键；其他自定义参数武器仍须分别确认参数表。
- 当前已确认参数表缺失或与参考项目别名完全无交集时，导入器必须显式失败；不允许把参考项目 `customizable: true` 装备作为未确认参数表的生产信源。

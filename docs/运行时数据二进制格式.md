# 运行时数据二进制格式

本文定义 `scripts/update-data.mjs` 生成、浏览器与优化 Worker 使用的运行时文件。`scripts/data/mcp-lumina.snapshot.json` 和参考项目原始导出仍是可复现输入；`src/data/generated-data.bin` 是经导入器校验后的生成产物，不得手工编辑。

## 目标与原则

- 一个无压缩的 `.bin` 承载完整运行时快照，所有运行时数据都是二进制编码，没有 JSON 文本段。
- 装备实体按适用的唯一主属性物理分组；多主属性或无法唯一确定主属性的装备放入独立 `SHARED` 组。实体只存一份，各物理组内按 `(品级升序, ID 升序)` 排列。
- 五个逻辑主属性索引合并引用对应单主属性组，以及 `SHARED` 组中适用于该主属性的实体，并按 `(品级升序, ID 升序)` 排列；它们用于查找和品级区间定位，不代替装备的物理分组存储。
- 读取时完整获取并校验二进制文件，初始化阶段快速解码五组紧凑索引；只解码当前职业主属性、配置品级区间内需要的装备对象。二进制容器、目录与索引会常驻；未选装备的原始记录字节留在缓冲区中，不构造 `Gear` 对象。
- 保留运行时需要的装备字段：`id`、`icon`、`name`、`slot`、`rawSlot`、`level`、`equipLevel`、`equipLevelVariable`、`roleId`、`jobCategory`、`stats`、`materiaSlots`、`materiaAdvanced`、`unique`、`customParameters`、`itemSpecialBonus`、`itemSpecialBonusParam`、`specialStats`、`source`、`jobs`、`sourceFile` 和 `dataSources`。
- 对应 `ResistanceWeaponAdjust` 非零行的武器或盾牌还保留 `resistanceWeaponAdjust: { maxTotalStats, maxEachStat, stats }`；`stats` 按 `BaseParam[0..3]` 顺序保存有效副属性名称。
- 不存 `weaponDamage`（从 `PDMG` / `MDMG` 推导）、`hq`、`customizable` 或 `rarity`。`jobCategory` 保留在运行时记录及历史结果中。可 HQ 装备的 `stats` 已合并 HQ 附加属性，`hq` 标志本身不参与运行时计算。
- 游戏数据合法性、来源完整性、字段范围和主属性引用只在生成阶段校验。读取阶段验证文件完整性、格式、段边界及索引结构，不再逐件重复业务合法性检查。

## 文件封装

所有整数均为 little-endian。文件以 16 字节头开始：

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 8 | ASCII magic：`FFXIVGDB` |
| 8 | 2 | 格式版本：`7` |
| 10 | 2 | flags：必须为 `0` |
| 12 | 2 | section 数量：必须为 `2` |
| 14 | 2 | header 长度：必须为 `40` |

头部后有两个 12 字节目录项：

| 项内偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 2 | section ID |
| 2 | 1 | codec：`0` 表示原样二进制 |
| 3 | 1 | 保留，必须为 `0` |
| 4 | 4 | 从文件开头算起的 payload 偏移 |
| 8 | 4 | payload 字节数 |

目录按 section ID 升序排列，payload 紧接目录。文件最后 4 字节是对文件前面全部字节计算的 CRC-32/ISO-HDLC（多项式 `0xEDB88320`，初始值和最终异或值均为 `0xFFFFFFFF`）。读取时校验整文件 CRC、连续偏移、文件长度、magic 和版本。单个整文件校验同时覆盖所有 section，避免重复扫描字节。截断、尾随数据、CRC 不符或不支持的版本均明确失败。

| ID | 名称 | 内容 |
|---:|---|---|
| 1 | `GAME_DATA_BINARY` | 版本、来源、食物、魔晶石、职业、等级与种族常数、属性上限等非装备数据 |
| 2 | `GEAR_CATALOG_BINARY` | 字符串表、来源模板、装备目录、主属性索引和装备记录 |

`GAME_DATA_BINARY` 中的同步品级映射也属于版本化运行时数据：`syncLevels` 的键为职业等级，值为该同步分组的升序品级数组；`syncLevelOfJobLevels` 的键为职业等级，值为同步分组没有精确匹配时使用的 fallback 品级。前者由 MCP `ContentFinderCondition` 的 `ClassJobLevelRequired`、`ItemLevelRequired` 与 `ItemLevelSync` 按参考转换流程生成；重复品级按行 ID 升序处理，后行覆盖前行。后者由 MCP `ParamGrow` 中对应职业等级行（50、60、70、80、90、100）的 `ItemLevelSync` 生成。参考项目 `src/game.ts` 的同名映射只用于最高职业等级以下的对照；最高等级的值是为后续版本预留的预测值，当前满级不会触发同级同步，因此不要求与该值一致。任何等级、品级映射无效、重复归属冲突或 MCP 分组转换结果与参考导出不一致都会使生成失败。

快照 `version` 直接保存所有 MCP 输入共同的游戏版本，不拼接策略或结构标签。结构变化由文件头格式版本区分；历史记录不依据数据版本进行业务判断。

`GAME_DATA_BINARY` 还保存食物的 `icon`、职业基础目录 `jobs` 和同步品级副本说明 `syncLevelDuties`。`jobs` 按项目职业缩写索引，每项为 `{ id, name, abbreviation }`，依次来自同版本 MCP `ClassJob` 行 ID、`Name`、`Abbreviation`；职业图标 ID 为 `id + 62100`。`syncLevelDuties` 按同步品级索引，每项为按行 ID 升序的 `{ id, name }` 数组，来自同版本 `ContentFinderCondition` 全表，仅保留 `ItemLevelSync > 0` 且 `JournalGenre != 0` 的行。没有独立版本字段或外置 JSON 目录，来源信息统一保留在快照和 provenance 中。

`equipLevelVariable` 的标志语义沿用参考项目 `data/convert.ts:140`：`Item.SubStatCategory` 值为 `2` 时装备属于可变穿戴等级装备；原始字段值来自同版本 MCP Item 查询。查询行按 `queryPlan` 中的装备和食物 ID 保存，并在 `snapshot.queries` 中保留字段、查询范围、游戏版本及查询时间；运行时装备的 `dataSources` 为该字段记录单独的来源 ID，避免把增量查询时间误记为原 Item 行时间。

装备原始属性还保留参考项目的 `main` / `secondary` 占位键，分别来自 MCP `Item.BaseParam=55/56`。二进制记录按职业解析前保留这两个键；领域候选生成会依照职业 Schema 映射为具体主、副属性。属性掩码使用 u32，以容纳包括这两个占位属性在内的全部属性代码。

没有 gzip 或其他压缩步骤。移除压缩可避免读取时的解压开销；文件体积会大于 gzip 结果，以实测生成产物记录为准。

## 通用二进制值

`GAME_DATA_BINARY` 与装备来源模板、逐件来源动态字段使用相同的类型标记编码。每段字符串表由字符串数 varuint、每个字符串的 UTF-8 字节长度 varuint 和 UTF-8 字节组成。对象键和值中的字符串引用表内序号；相同字符串在该段只保存一次。

| tag | 值 | 后续内容 |
|---:|---|---|
| `0` | null | 无 |
| `1` | false | 无 |
| `2` | true | 无 |
| `3` | i32 | 4 字节有符号整数 |
| `4` | u32 | 4 字节无符号整数 |
| `5` | f64 | 8 字节浮点数 |
| `6` | string | 字符串表序号 varuint |
| `7` | array | 元素数 varuint，随后逐项编码 |
| `8` | object | 字段数 varuint，随后为键字符串序号和值 |

安全整数优先编码为 i32 / u32；范围外安全整数和非整数编码为 f64。读取器直接建立 JS 值，不经 JSON 文本解析。

## `GEAR_CATALOG_BINARY`

该 section 顺序包含以下字段：

1. 装备属性并集掩码 u32、全局最低品级 u16、全局最高品级 u16。
2. 装备字符串表：字符串数 u32、`count + 1` 个 u32 偏移、UTF-8 字节区。偏移相对 UTF-8 字节区起点；同一字符串只保留一份，读取器保存偏移并按需解码实际引用的字符串。
3. 来源模板长度 u32 和模板数组的通用二进制值。
4. 物理存储组数 u8（固定为 6）。依序写入 `VIT, STR, DEX, MND, INT, SHARED`：组代码 u8、装备数 u32、记录体字节数 u32。
5. 装备目录。按物理组顺序排列，每条目录项 10 字节：装备 ID u32、品级 u16、组内记录体偏移 u32。偏移相对该物理组记录体起点；组内记录体长度由下一项偏移相减得到，最后一项长度由组记录体总长确定。
6. 逻辑主属性索引数 u8（固定为 5）。依次写入 `VIT, STR, DEX, MND, INT`：主属性代码 u8、引用数 u32、全局记录序号 u32 数组。全局记录序号按照物理组顺序以及组内目录顺序编号。
7. 六个物理组的记录体字节区，依 `VIT, STR, DEX, MND, INT, SHARED` 顺序连续存放。

若装备 `jobs` 对应的职业全部只有同一个 `mainStat`，该实体进入相应的 `VIT`、`STR`、`DEX`、`MND` 或 `INT` 物理组。若适用职业跨多个主属性，或没有可确定的唯一主属性，则进入 `SHARED` 组。每件装备恰好有一个物理存储位置。

每个物理组内部严格按 `(level, id)` 升序。ID 与品级只在目录中存一份；记录体不重复存这两项。逻辑 `mainStat` 索引包含对应单属性组和 `SHARED` 组中至少有一个适用职业属于该主属性的记录序号，并按同样的 `(level, id)` 顺序合并排序。因此可对当前品级区间二分定位，同时只解码被选中的记录体。主属性索引以连续 u32 数组存储，并在初始化时一次性快速解码；实际索引条目数与内存成本由生成的快照统计。

### 装备记录体

装备记录体按以下顺序编码：

| 字段 | 编码 | 说明 |
|---|---|---|
| `slot` | u8 | `weapon, offhand, head, body, hands, legs, feet, earrings, necklace, bracelet, ring` 的序号 |
| `icon` | u32 | 同版本 MCP `Item.Icon`，必须为正整数 |
| `equipLevel` | u8 | 穿戴等级 |
| `rawSlot` | u8 | 上游原始槽位 |
| `roleId` | u8 | 角色分类 ID |
| `jobCategory` | u16 | 上游职业分类 ID，按用户要求保留 |
| `materiaSlots` | u8 | 魔晶石孔数 |
| `flags` | u8 | 下表定义 |
| `jobCount` | u8 | 适用职业数 |
| `jobIndexes` | u8 × `jobCount` | `jobSchemas` 键顺序的职业序号，保留原顺序 |
| `statMask` | u32 | 后续存在的属性位图 |
| `statValues` | i16 × 置位数 | 按 `STR, DEX, INT, MND, VIT, CRT, DET, DHT, SKS, SPS, TEN, PIE, PDMG, MDMG, DLY, main, secondary` 顺序 |
| `customParameterCount` | u8 | 自定义武器参数数量 |
| `customParameters` | 每条 11 字节 | `materiaId` u32、`statCode` u8、`bigValueIndex` u8、`smallValueIndex` u8、`bigValue` u16、`smallValue` u16 |
| `resistanceWeaponAdjust` | 由 flags 控制，最长 16 字节 | 存在时为 `maxTotalStats` u32、`maxEachStat` u32、`statCount` u8、`statCodes` u8 × `statCount` |
| `itemSpecialBonus`, `itemSpecialBonusParam`, `specialStats` | 由 flags 控制，最短 12 字节 | 存在时为 `itemSpecialBonus` u32、`itemSpecialBonusParam` u32、特殊属性掩码 u32 和每个置位属性的 i16 值 |
| `nameStringId` | varuint | 装备名称字符串表序号 |
| `sourcePresent` | u8 | `0` 无 `source`，`1` 后接 source 字符串序号 |
| `sourceFileStringId` | varuint | 生成来源文件字符串序号 |
| `dataSourceCount` | varuint | 逐件来源记录数 |
| `dataSources` | 变长 | 每项是来源模板序号、动态字段掩码及存在的 `rowIds` / `sourceFiles` 通用二进制值 |

`flags` 位定义：`0x01` 表示 `materiaAdvanced: true`；`0x02` 表示 `unique: true`；`0x04` 表示 `equipLevelVariable: true`；`0x08` 表示存在 `resistanceWeaponAdjust`；`0x10` 表示存在 `itemSpecialBonus`、`itemSpecialBonusParam` 和 `specialStats`。未置位均按 false 处理，不使用额外字段存在标记。可变穿戴等级标志只在 MCP `Item.SubStatCategory === 2` 时置位；该标志影响候选属性封顶与魔晶石处理，不排除装备候选。其他位保留且必须为零。`customParameters` 数量大于零时才重建此可选字段。自定义属性代码为 `CRT, DET, DHT, SKS, SPS, TEN, PIE` 的序号。`resistanceWeaponAdjust` 的 `statCodes` 使用相同顺序和代码表，必须至少有一个且不得重复。

`resistanceWeaponAdjust` 从 MCP `ResistanceWeaponAdjust` 中与 Item ID 同号的行生成。全量查询产物（包括空行 0）、Schema 字段、查询范围、游戏版本与查询时间保存在 MCP 快照；非零行 ID 均加入 Item 查询范围。`MaxTotalStats` 和 `MaxEachStat` 原样成为 u32 上限；非零 `BaseParam[0..3]` 通过 MCP `BaseParam` ID 映射为可调整属性。运行时模型对这些属性使用 0 下限和整数步进，因此上限之间的每个整数值均可表示。

`ItemSpecialBonus` 当前仅支持 MCP `Item` 中的 ID `11`。生成时仅对此 ID 保存 `itemSpecialBonus`、`itemSpecialBonusParam` 和从 `BaseParamSpecial[0..5]` / `BaseParamValueSpecial[0..5]` 读取的独立 `specialStats`；它使用与 HQ 属性相同的 BaseParam 映射和武器伤害筛选规则。ItemSpecialBonus ID 及参数来自同版本 Item 查询，支持 ID 的描述来自 MCP `ItemSpecialBonus` 行查询。ID 11 的 Special 属性不再并入普通 `stats` 的 HQ 合并，避免启用特殊效果时重复计入；其他装备的 HQ 合并行为不变。二进制中的特殊属性掩码使用与普通装备属性相同的 STAT 代码表及 i16 值。

来源模板包含除逐件 `rowIds` 和 `sourceFiles` 外的来源字段；逐件动态值保留在各自记录体中。所有装备均保存 `sourceFile` 和完整 `dataSources`，满足来源追溯要求。

## 生成与读取

### 生成

1. `scripts/update-data.mjs` 从 MCP 查询快照和参考项目原始导出构造全量运行时快照，并校验必需字段、来源、数值范围、职业引用、装备来源、属性数据和适用主属性。同步品级分组来源为 MCP `ContentFinderCondition`；等级到精确品级的 fallback 来源为 MCP `ParamGrow` 对应等级行（50–100）的 `ItemLevelSync`，并与参考项目 `src/game.ts` 在最高等级以下逐值核对。`ResistanceWeaponAdjust` 全表与同 ID Item 行必须完整、同版本且有查询来源。
2. 投影到上文列出的运行时装备字段；`weaponDamage` 由武器属性恢复，不写入文件。`jobCategory` 保留；`hq`、`customizable` 和 `rarity` 不写入运行时记录。食物保留完整目录，搜索候选的伤害属性筛选与帕累托剪枝在运行时进行。匹配的 Resistance Weapon 装备会保存 `MaxTotalStats`、`MaxEachStat` 与可调整属性集合。
3. 对装备名称、来源、来源文件和来源动态值建立段内字符串表；对重复来源模板建立模板表。
4. 按适用职业的主属性集合决定物理组：集合只有一个主属性时进入该主属性组，否则进入 `SHARED`。各组分别按 `(品级, id)` 排序；五组逻辑主属性索引引用相应主属性组及 `SHARED` 组的目录序号，并按相同键合并排序。记录目录偏移、组别、索引排序及引用范围在生成阶段校验。
5. 写入两个二进制 section 和 CRC-32，生成 `src/data/generated-data.bin`。MCP 快照及参考导出是输入来源；禁止手工编辑生成文件。

### 读取

1. 浏览器与优化 Worker 加载完整 `.bin` 缓冲区。单文件模式不减少网络传输字节。
2. 验证整文件 CRC-32、容器头、目录连续性和格式版本；解码全部非装备数据、装备字符串偏移、目录和五组主属性索引，不创建装备对象。
3. `gearOptionsFor` 使用已解码的主属性索引，按索引中记录目录的品级列二分定位配置区间，只解码和缓存区间内的装备记录。职业、槽位、装备等级、可变穿戴等级标志及来源排除等既有过滤逻辑继续应用；可变等级装备仍进入候选，穿戴等级为 1 的装备只在计算等级基准选择时忽略。被索引选中的实体保持 `(level, id)` 顺序。
4. `getGearById` 用目录 ID 映射按需解码单条被配置引用的装备。当前主属性只读取其单属性物理组与 `SHARED` 组中的索引区间。保留 `gears` 的惰性数组兼容视图；显式遍历整表会解码全部记录，运行时热点使用索引和 ID 查找接口。
5. `weaponDamage` 由 `stats.PDMG ?? stats.MDMG` 恢复。搜索 Worker 与 UI 模块各自在自己的执行环境中维护解码缓存，不通过 structured clone 传输整表。
6. 格式错误或 CRC 不符时终止读取，不回退旧 JSON 或内置数据。业务合法性由生成器保证，读取器不逐件复验。

## 性能记录

格式版本 7 增加物品图标、职业基础目录及同版本同步副本说明；格式版本 6 增加 ItemSpecialBonus 及独立 Special 属性；格式版本 5 增加 Resistance Weapon 可调整属性集合与上下限；格式版本 4 增加 `main` / `secondary` 原始属性及 u32 属性掩码。下列旧版本数据不能代表当前二进制性能。

以下数据是格式版本 2 产物的历史测量，不代表当前格式版本 7。测量使用 `npm run data:benchmark -- 7`，另先运行 1 轮预热。输入文件已在内存中，因此下表不含文件读取或浏览器网络时间；初始化包含整文件 CRC。完整解码包含全部 22,023 条装备记录及逐件来源还原。来源耗时拆分为共享模板解码和逐件来源元数据解析；每件装备其余字段另行计时。逐字段计时启用 `onTiming` 回调，会增加少量观测开销；完整解码数据包含这部分开销。

测量环境：Node v26.5.0，Windows 10.0.22631 x64，12th Gen Intel Core i7-12650H。当时格式版本 2 快照为 2,458,425 字节；同版本 JSON 为 42,383,569 字节，gzip JSON 为 1,006,711 字节。主属性索引共 32,023 条 u32 引用，占 128,092 字节。表中为中位数和 p95 毫秒；7 轮下 p95 等同于观测最大值。

# 运行时数据二进制格式

运行时仅保存 `src/data/generated-data.bin`，由 `npm run data:update` 从同次 MCP 查询及固定 commit 的参考资料直接生成。查询结果只存在于内存中，不保存 JSON 中间文件或原始行档案。禁止手工编辑生成文件。

## 格式定义与维护

格式版本为 13。精确字段定义以 `src/data/binary` 下的 TypeScript Schema 为准：容器定义在 `schema.ts`，十个业务模块各自维护 `sections/<业务>/schema.ts`。读取与写入分别使用这些 Schema，不使用通用对象值编码，也不存储 JSON 文本段。

运行 `npm run data:format` 从 Schema 生成[字段文档](generated/运行时二进制字段.md)，`npm run data:format:check` 校验文档未过期。本文维护格式语义、读取策略和算法布局，不重复手写业务字段表。Schema 是项目内部的格式契约，不需要在网站运行时加载外部定义文件。

## 容器

所有固定宽度整数使用 little-endian。起始为 8 字节 ASCII `FFXIVGDB`，随后为 Schema 定义的版本、flags、段数和头长度；版本必须为 13，flags 必须为 0，段数必须为 10，头及段目录共 136 字节。十个 12 字节目录项按段编号升序保存，codec 和保留位为零。payload 紧接目录，偏移连续且不重叠。段编号及目录字段由 Schema 和生成字段文档维护。

文件最后 4 字节为此前全部字节的 CRC-32/ISO-HDLC（多项式 `0xEDB88320`，初始值及最终异或均为 `0xFFFFFFFF`）。读取完整文件并检验长度、CRC、magic、格式版本、段目录及边界；截断、尾随字节、不支持版本和非法引用均失败。不压缩，不回退旧格式或 JSON。

结构变化时更新格式版本并重生成产物；前端、Worker 和 Node 使用同一解码契约，不要求向前兼容旧格式。游戏数据版本仍为 MCP 的实际游戏版本，与结构版本分开。

## 普通业务段

每个非装备段先写独立字符串表，再按该段 Schema 写入根记录。字符串表用 varuint 记录数量及每个 UTF-8 字符串的字节长度，字符串字段只保存表内序号。每条记录按 Schema 顺序写值，不写字段名称；可选字段按字段数使用 u8（1～8 项）、u16（9～16 项）或 u32（17～32 项）存在位图，存在位的顺序与 Schema 一致，保留位必须为零。数组先写 varuint 数量，数值索引表或枚举索引表只写已定义的键类型。非规范或超出安全整数的 varuint、非法枚举、非有限数值、重复索引及非法 UTF-8 均失败。

普通记录由同一份 Schema 驱动读取与写入；解码器不包含编码器入口。数值按字段定义选择宽度，小数使用 f64 保持原始精度。只有基础属性规则存在明确的三分支类型码（main/sub/数值），不支持任意对象或动态类型编码。文本字段即使内容恰好类似 JSON，也仍只是普通文本。

`METADATA` 保存游戏版本和全局 provenance 摘要：参考仓库 URL、精确 commit、导入时间。逐项溯源、源文件、查询范围、版本警告与能力核验证据仅用于生成阶段的内存校验，不写入任何运行时业务段。装备获取途径 `source` 用于筛选和展示，继续保留。

`JOBS` 仅保存统一的职业 `mainStat`，取值为力量、灵巧、智力或精神，不再编码独立 `attackStat`。坦克与力量 DPS 通过 `role` 和装备适用职业区分；装备目录仍保留五个主属性索引和六个物理组，允许未使用的 VIT 索引与物理组为空。

`ITEM_LEVEL_CAPS` 保存升序品级数组、按内容去重的上限列数组，以及按 CAP_COLUMNS 顺序排列的列引用。品级和上限值均为 u16；读取时检查数组长度、字典唯一性、引用完整性及范围，展开为完整的独立属性列，不硬编码哪些属性相同。`FOODS` 的固定加成使用 u16、比例直接使用 u8，不使用比例字典；装备 ID 和食物及装备图标 ID 保持 u32。整数编码字段必须在生成时拒绝负数、小数和超范围值，不截断或钳制。

`SYNC` 保留整理后的等级下界、默认品级和分类名称/目标；读取时复核支持等级、目标与上限的引用关系及唯一性，不重做副本分类。生成业务规则见[数据规则](rules/数据规则.md)。

## 装备目录算法布局

`GEAR_CATALOG` 顺序保存：

1. 属性并集掩码 u32、最低和最高品级各 u16。
2. 独立名称池和获取途径池：各为 varuint 数量、逐项 varuint UTF-8 字节长度和拼接字节区。初始化累计长度构造内存偏移；字符串按需解码和缓存。
3. 属性掩码字典：varuint 数量及逐项 u32 掩码，普通与特殊属性共同使用。
4. 职业组合字典：varuint 数量，每项保存 jobCategory u16 及适用职业序号数组。字典按实际分类 ID 和有序职业列表去重，保留分类差异。
5. 物理组数 u8 及六个物理组描述符，顺序为 VIT、STR、DEX、MND、INT、SHARED。
6. 按物理组顺序保存装备目录项：ID u32、品级 u16、记录字节长度 varuint。初始化累计各组长度恢复内存偏移，长度之和须匹配组描述符。
7. 逻辑主属性索引使用显式宽度 2 或 4 字节；记录数不超过 65536 时为 u16，否则为 u32。五个主属性索引头及序号数组保持原有语义。
8. 六个物理组的记录体字节区，按物理组顺序连续保存。

名称、获取途径、属性掩码与职业组合的引用宽度由各池或字典数量确定：不超过 256 项用 u8，不超过 65536 项用 u16，否则用 u32。引用必须在对应范围内；字典和索引数量不成为业务上限。

每件装备只存一份。适用职业只有一个主属性时进入该物理组，否则进入 SHARED。物理组内与逻辑索引均按 `(品级, ID)` 严格升序。逻辑索引合并对应单属性物理组与适用于该属性的 SHARED 记录。读取时校验 ID、目录排序、品级边界、逻辑引用范围、排序与物理组归属，以及所有记录范围；不为此构造装备对象。

### 装备记录体

记录固定头、目录项、组描述符和索引头均有可执行 Schema，精确字段顺序见生成字段文档。固定头后依次保存：

1. 职业组合引用，字典中的职业序号对应 JOBS 段 jobSchemas 的键顺序。
2. 属性掩码引用及按属性代码顺序保存的 u16 值；位图保留 main/secondary 占位属性。普通与特殊属性值均须在生成时检查为 0～65535 的整数。
3. 仅在 flags 指示自定义参数存在时写入数量 u8；每条为 materiaId u32、statCode/bigValueIndex/smallValueIndex 各 u8、bigValue/smallValue 各 u16。
4. flags 指示的义军调整结构：总上限、单项上限各 u32，属性数 u8，属性代码 u8 数组。
5. flags 指示的特殊效果结构：效果 ID、参数各 u32，后接属性掩码引用及按属性代码顺序保存的 u16 值。
6. 名称池引用；仅在 flags 指示获取途径存在时后接获取途径池引用。记录至此结束。

flags、槽位及属性代码表由装备 Schema 维护。flags 的 bit5 为获取途径存在、bit6 为自定义参数存在，bit7 保留且必须为零。jobCategory、图标、可变穿戴等级、义军及特殊效果字段继续保留。装备 ID 和 icon 均为 u32；weaponDamage 从 PDMG/MDMG 恢复；hq、customizable、rarity、sourceFile、dataSources 不写入文件。

## 生成与读取边界

更新器先固定参考 commit，再执行同版本 MCP 查询、来源及完整业务校验（包括版本警告例外和 BLU 缺失资料回退依据）。校验通过后显式投影为运行时字段，删除逐项溯源和详细查询证据；低层二进制写入器只负责运行时格式，不替代上游核验。数据编码到临时文件，读取并遍历全部装备，检查目录身份并重编码复核字节一致后才替换最终 bin；失败删除临时文件、保留旧 bin。只有最终 bin 是长期生产产物。

运行时完整读取并验证文件，初始化非装备业务段、装备目录与紧凑索引。品级区间通过逻辑主属性索引二分定位，只解码所需记录；getGearById 直接定位单件。惰性 gears 数组保留兼容视图，显式遍历才会构造全体对象。浏览器与各 Worker 分别维护解码缓存，不 structured clone 整表。

版本 9 及更早版本的二段布局、通用对象值编码和历史性能测量不代表本格式。新格式性能以相同输入、相同设备的 `npm run data:benchmark` 实测为准。

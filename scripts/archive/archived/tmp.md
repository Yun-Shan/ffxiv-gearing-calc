旧组合 `N` 几千万到上亿，新 node `M` 几十个，每条固定 4 个字段，每个字段 16bit，相加后仍不超过 16bit，使用 JS。

---

## 1. CPU 多线程 + 分块排序 + 多路归并去重

这是首选方案，核心原因是：**排序后加常数仍然有序**。

如果旧组合按 `(f0,f1,f2,f3)` 字典序升序排好，那么对任意一个新 node `t`，集合 `{ s + t | s ∈ S }` 仍然保持同样的字典序。因为每个字段都加同一个常数，且不溢出，单调性不变。

所以不需要全局 `Set`，也不需要全局哈希表。几十个新 node 只会产生几十个有序流，直接多路归并即可。

### 推荐流程

1. **旧组合分块**  
   不要把上亿条全部加载后一次性排序。按块处理，例如每块 500 万到 2000 万条。  
   每块读入内存，块内排序，然后与所有新 node 做归并。

2. **块内排序**  
   按 `(f0,f1,f2,f3)` 升序。  
   因为字段是 16bit，可以用四轮 16 位基数排序，速度比 `Array.sort` 快很多。

3. **块内笛卡尔积归并**  
   对当前块 `S_block`，有 `M` 个新 node。  
   对每个新 node `t`，生成流 `S_block + t`。  
   因为 `S_block` 有序，所以每个流都有序。  
   用大小为 `M` 的最小堆做多路归并，输出当前块的所有结果。  
   归并时顺便去重：相同元组一定相邻。

4. **每个块输出一个临时有序文件**  
   当前块处理完，得到一个“块内有序且去重”的临时文件。  
   所有块可以分配给 Node.js `Worker` 并行处理。

5. **最终多路归并**  
   所有块处理完后，得到 `K` 个有序临时文件。  
   对这 `K` 个文件再做一次多路归并，输出去重后的最终结果。

### 为什么这样内存低

- 旧组合不需要全部进内存，只需要当前块。
- 去重不需要 `Set`，只比较上一个输出元组。
- 临时文件顺序写、顺序读，IO 友好。
- 并行时每个 Worker 独立处理一个块，互不干扰。

## 2. JS 实现细节：打包、基数排序、最小堆归并

### 2.1 用两个 Uint32 打包一条组合

不要用 `BigInt`，也不要存成对象。  
每条组合 4 个 16bit 字段，可以打包成两个 `Uint32`：

```js
// f0, f1, f2, f3 都是 0..65535
key0 = (f0 << 16) | f1; // 高16位是 f0，低16位是 f1
key1 = (f2 << 16) | f3; // 高16位是 f2，低16位是 f3
```

这样一条组合只占 **8 字节**。  
1 亿条约 **800MB**。

排序和比较时：

- 先比较 `key0`
- `key0` 相同再比较 `key1`

这等价于按 `(f0,f1,f2,f3)` 字典序升序。

加法时，新 node 也打包：

```js
tk0 = (t0 << 16) | t1;
tk1 = (t2 << 16) | t3;
```

结果：

```js
r0 = (s_key0 + tk0) >>> 0;
r1 = (s_key1 + tk1) >>> 0;
```

因为题目保证每个字段相加后仍在 16bit 内，所以：

- `f1 + t1` 不会超过 `0xFFFF`，不会进位到 `f0`
- `f3 + t3` 不会超过 `0xFFFF`，不会进位到 `f2`
- `r0`、`r1` 都不会超过 `0xFFFFFFFF`

所以直接用 `Uint32Array` 存结果即可。

解包：

```js
f0 = r0 >>> 16;
f1 = r0 & 0xFFFF;
f2 = r1 >>> 16;
f3 = r1 & 0xFFFF;
```

### 2.2 基数排序

对每块数据，用四轮 16 位计数排序：

1. 按 `f3` 排序
2. 按 `f2` 稳定排序
3. 按 `f1` 稳定排序
4. 按 `f0` 稳定排序

每轮计数数组大小 `65536`，用 `Uint32Array(65536)`。  
需要两个缓冲区 `src` 和 `dst`，都是 `Uint32Array(2 * blockSize)`。  
每轮从 `src` 读，写 `dst`，然后交换。

伪代码：

```js
function radixSortBlock(src, dst, n) {
  // src/dst 长度 2*n，每条两个 Uint32
  // 依次按 f3, f2, f1, f0 排序
  // 每轮：
  //   1. 统计计数
  //   2. 前缀和
  //   3. 稳定放置
  //   4. 交换 src/dst
}
```

排序后，块内数据按 `(f0,f1,f2,f3)` 升序。

### 2.3 多路归并最小堆

堆大小只有 `M`，几十个，很小。  
但候选数可能是几十亿，所以**不要在循环里创建对象**，否则 GC 会拖死。

可以用几个平行数组表示堆：

```js
const heapT = new Int32Array(M);  // 新 node 索引
const heapS = new Int32Array(M);  // 当前块内旧组合索引
const heapK0 = new Uint32Array(M); // 当前结果 key0
const heapK1 = new Uint32Array(M); // 当前结果 key1
let heapSize = 0;
```

比较规则：

```js
// a 比 b 小：heapK0[a] < heapK0[b] ||
//           heapK0[a] === heapK0[b] && heapK1[a] < heapK1[b]
```

初始化：

```js
for (let t = 0; t < M; t++) {
  const s = 0;
  const r0 = (blockKey0[s] + tk0[t]) >>> 0;
  const r1 = (blockKey1[s] + tk1[t]) >>> 0;
  push(t, s, r0, r1);
}
```

循环：

```js
let last0 = -1, last1 = -1;
let outCount = 0;
const outBuf = new Uint32Array(OUT_BUF_SIZE * 2);

while (heapSize > 0) {
  const min = pop(); // 返回 t, s, r0, r1

  // 去重：因为所有流有序，重复一定相邻
  if (min.r0 !== last0 || min.r1 !== last1) {
    outBuf[outCount * 2] = min.r0;
    outBuf[outCount * 2 + 1] = min.r1;
    outCount++;
    last0 = min.r0;
    last1 = min.r1;

    if (outCount === OUT_BUF_SIZE) {
      writeBinary(outBuf, outCount);
      outCount = 0;
    }
  }

  // 同一新 node 的下一个旧组合
  const nextS = min.s + 1;
  if (nextS < blockSize) {
    const nr0 = (blockKey0[nextS] + tk0[min.t]) >>> 0;
    const nr1 = (blockKey1[nextS] + tk1[min.t]) >>> 0;
    push(min.t, nextS, nr0, nr1);
  }
}
```

输出时不要拼字符串，直接写二进制：

```js
const buf = Buffer.from(outBuf.buffer, 0, outCount * 8);
stream.write(buf);
```

### 2.4 最终归并

每个块输出一个临时文件。  
最终对 `K` 个临时文件做同样的多路归并，只是流从“新 node + 旧组合块”变成“临时文件”。  
每个文件顺序读，堆大小是 `K`，同样去重。

## 内存占用优化总结

### 数据表示

- 4 个 16bit 字段打包成两个 `Uint32`，每条 **8 字节**。
- 1 亿条约 **800MB**。
- 不要用对象、数组嵌套、BigInt。

### 分块处理

- 每块 500 万到 2000 万条。
- 每块 1000 万条：原始数据 80MB，排序双缓冲 160MB。
- 计数数组 `65536 * 4 = 256KB`。
- 堆大小只有 `M` 几十，可忽略。
- 输出缓冲 1MB 左右。

如果开 16 个 Worker，每个 Worker 独立处理一块：

- 总内存约 `16 * 160MB = 2.5GB` 左右。
- 如果内存小，减少块大小或 Worker 数。

### 排序内存

- 基数排序需要 `src` 和 `dst` 两个缓冲区，峰值是数据量的 2 倍。
- 排序完可以释放一个缓冲区，或复用为输出缓冲。

### 归并内存

- 多路归并只维护堆和当前读缓冲。
- 最终归并只读 `K` 个临时文件，不全部加载。
- 去重只保存上一个输出元组，不需要 `Set`。

### 输出内存

- 直接写二进制 `Uint32Array`。
- 不要先转成 JSON、字符串或对象数组。
- 如果最终结果还要给别的系统，保持二进制格式最省内存。

### 临时文件

- 每个块一个临时有序文件。
- 如果临时文件太多，可以多阶段归并。
- 磁盘空间要足够，因为候选可能几十 GB，**不要使用默认的tmp目录，因为默认tmp目录在C盘且C盘空间一般很少**。

---

## 结论

- **首选：CPU 多线程 + 分块 + 基数排序 + 多路归并去重。**
- **JS 实现关键：两个 Uint32 打包一条、四轮 16 位基数排序、无对象的最小堆归并、流式二进制输出。**
- **内存优化关键：分块、双缓冲排序、共享/复用缓冲、去重只存 last、临时文件顺序读写。**
